# 개인 커리어 브레인 — 오픈소스 레포 구축 계획

작성 기준: 2026-11-16  
레포 가칭: `career-brain`  
상태: 설계 제안. 레포 생성·배포·성능 시험을 수행한 결과가 아니다.

## 1. 목표와 범위

개인이 자신의 서버에서 경력·프로젝트·학습·문서·관심 공고·지원 이력을 보관하고, 웹 대시보드와 AI 도구를 통해 관리하는 완결된 오픈소스를 만든다. 클라우드 서비스 가입이나 유료 라이선스 서버 없이 핵심 기능이 동작해야 한다. 외부 모델·OCR·검색 API 사용 비용은 소프트웨어의 무료 배포와 구분한다.

이 레포는 다음 두 역할을 함께 가진다.

1. 바로 설치해서 쓰는 개인용 제품: React 개인 대시보드, FastAPI 실행 앱, PostgreSQL, 작업 실행기, 설치·백업 도구.
2. 서비스 레포가 재사용하는 공통 엔진: Python 패키지, API 계약, 문서 편집·근거 표시용 UI 구성요소, MCP 도구, 업무 스킬.

공개 서비스의 마케팅 화면·회원 운영·결제·플랜·운영자 화면·운영용 배포 설정은 다른 레포에서 개발한다. 이 레포에 `IS_CLOUD` 분기를 계속 추가해 하나의 앱을 두 제품으로 억지 분기하지 않는다.

공고 전체를 긁어 오는 시스템은 범위 밖이다. 사용자가 정한 관심 기업·조건·저장 공고만 탐색·추적하며, 관심 없는 공고 본문은 영구 적재하지 않는다. 세컨드 브레인은 취업 자료에만 제한하지 않고 사용자가 직접 저장한 일반 지식·학습 자료도 수용한다.

## 2. 두 레포의 관계

```text
career-brain [공개]
  공통 엔진 + 개인용 API 실행 앱 + 개인 대시보드
  Python wheel / TypeScript 패키지 / 스킬 팩 배포
                         │ 버전 고정 의존성
                         ▼
career-service [기본 비공개]
  서비스 프론트 + 서비스 백엔드 + 회원·결제·운영
```

의존 방향은 서비스 → 공통 엔진 하나로 제한한다. 공개 레포가 비공개 모듈을 import하거나, 기본 실행에 서비스 전용 API를 요구해서는 안 된다. 서비스 레포에 코어 소스를 복사하지 않고 고정된 배포 패키지를 설치한다.

두 레포는 두 API 서버를 반드시 네트워크로 연결한다는 뜻이 아니다. 서비스 실행 앱은 코어를 라이브러리로 조립해 API 프로세스 하나로 실행할 수 있다. 개인용 API 실행 앱은 그 자체의 별도 설치 환경에서 실행한다. 개인용 DB와 서비스 DB도 별개이며 기본적으로 동기화하지 않는다.

## 3. 라이선스 방침

공통 엔진과 개인 대시보드는 Apache-2.0을 우선 제안한다. 서비스 백엔드가 공통 엔진을 직접 import하면서 자체 코드는 비공개로 유지하는 구성을 단순하게 하기 위한 선택이다. 고지·라이선스·NOTICE 등 원 라이선스의 조건은 준수한다. 기존에 검토한 AGPL 프로젝트 코드를 단순히 가져와 Apache-2.0으로 바꾸지 않는다. 외부 의존성·템플릿·모델·폰트·자료의 라이선스는 별도 목록으로 관리한다. [S1]

공개 저장소에 실제 개인정보, 회사 자료, 사용자 DB, 모델 키, 브라우저 쿠키, 운영 로그를 넣지 않는다. 데모는 합성 데이터를 사용한다. 저장소 공개 전 현재 파일뿐 아니라 Git 이력도 검사한다.

## 4. 레포 구조

```text
career-brain/
  apps/
    personal-web/                 # React + TypeScript + Vite + shadcn/ui
    personal-api/                 # FastAPI composition root, 개인 로그인·설정
  packages/
    core/
      pyproject.toml
      src/career_core/
        domain/                  # 업무 개념·상태·규칙
        usecases/                # 읽기·작성·확정·수집·학습의 공통 처리
        ports/                   # 외부 기능 인터페이스
        db/                      # SQLAlchemy 모델·저장소
        migrations/              # 코어 테이블의 Alembic revision
        adapters/                # pgvector·파일·OCR·모델·검색 연결
        workflows/               # 필요한 LangGraph 흐름
        jobs/                    # 작업 핸들러와 큐 어댑터
        interfaces/http/         # 공통 FastAPI routers
        interfaces/mcp/          # 선별한 MCP tools
    ui/                          # 문서 편집·변경 비교·근거 카드
    client/                      # 인증·기본 URL을 주입받는 TS 클라이언트
  contracts/                     # OpenAPI·JSON Schema·호환성 문서
  skills/                        # 업무 지침과 합성 예제
  deploy/compose/                # 개인용 compose·Caddy
  tests/{unit,integration,e2e,security,fixtures}/
  docs/{architecture,operations,contributing}/
```

`packages/core`에는 결제 SDK, 서비스 도메인, 광고 분석, 고객 지원 전용 로직을 넣지 않는다. `packages/ui`에는 앱 전체 네비게이션이나 SaaS 가입 흐름을 넣지 않는다.

## 5. 기본 기술과 실행 구조

> 구현하면서 바뀐 점 (현재 구조는 [overview.md](overview.md)): 작업 큐는 Procrastinate 대신 PostgreSQL 표 `core.jobs` + `claim_job`·lease·`LISTEN/NOTIFY`로 직접 만들었다. 문서 편집은 Tiptap 없이 문단 블록 편집기로 했다. Caddy는 기본 구성에 넣지 않고 설치 문서에 리버스 프록시 예시로만 둔다. 아래 원문은 설계 당시 기록이다.

- 프론트: React·TypeScript·Vite·shadcn/ui, 서버 상태는 TanStack Query, 폼과 검증은 일관된 스키마 기반으로 구성.
- 서버: FastAPI·Pydantic·SQLAlchemy·Alembic. 라우터는 요청 검증과 유스케이스 호출만 담당.
- DB: PostgreSQL, 의미 검색은 pgvector, 유사 문자열은 pg_trgm. 별도 OpenSearch·Neo4j·벡터 DB를 필수로 두지 않는다.
- 큐: Procrastinate를 `JobQueue` 어댑터 뒤에 배치. 주기 작업·재시도·잠금은 활용하되 교체 가능하게 한다. 해당 프로젝트는 유지보수자 모집도 안내하므로 버전과 운영 상태를 점검한다. [S2, S3]
- 문서 편집: Tiptap 오픈소스 코어. AI·버전·비교 기능은 우리의 코어와 UI로 구현하며 Pro 확장을 무료 기본 기능으로 가정하지 않는다. [S4]
- AI: 외부 모델 제공자 어댑터. MCP를 통한 외부 AI 호출은 모델 사용과 분리한다.
- 파싱: 가벼운 텍스트·HTML·문서 추출 우선. 복잡한 PDF·스캔 자료는 허용된 PaddleOCR·MinerU API. 로컬 OCR 모델 상시 실행은 기본 구성에 없다. [S5, S6]

```text
PC·모바일 → Caddy → personal-web 정적 파일
                    └→ personal-api → core usecases
                                         ├→ PostgreSQL
                                         ├→ 비공개 파일 볼륨
                                         └→ 작업 큐 → worker
외부 AI → 인증된 MCP → 동일한 core usecases
```

작은 서버에서는 `personal-api serve` 한 프로세스가 API·worker(별도 스레드)·웹 정적 파일을 함께 맡는다 (설치: `docs/operations/install.md`, 언어 선택 근거: `docs/architecture/rust.md`). 상시 컨테이너는 Caddy·API·PostgreSQL·worker를 기본으로 한다. 스케줄러는 worker 계열의 가벼운 루프로 실행하고 동일 주기 작업을 중복 등록하지 않도록 잠근다. 브라우저는 필요 작업에만 켜며 기본 웹 서비스와 분리된 권한으로 실행한다.

공통 조건:
- 개인 관계 테이블의 외래키에도 공간 일치 제약을 둔다. UUID만 맞으면 다른 공간의 자료를 연결할 수 있게 하지 않는다.
- 시간은 UTC로 저장하되 원본 시간대와 사용자의 표시 시간대를 보존한다. 마감 시각이 없으면 추측하지 않는다.
- 크롤링 실패·로그인 필요·접근 차단과 채용 마감을 구분한다.
- 검증 상태는 최소 `extracted / self_confirmed / evidence_supported / disputed / retired`를 구분한다. 팀 성과와 본인 기여도 분리한다.
- 개인정보 원본과 제출용·공개용 사본은 다른 객체다.

## 8. 공고 저장 흐름

### 1차 범위: URL 저장

사용자가 공고 URL을 붙여넣을 때만 그 페이지 한 건을 가져온다. 여러 URL을 한 번에 붙여넣을 수 있다. 사이트를 돌아다니는 수집, 주기 재확인, 회사 구독, 조건 검색은 1차 범위에 넣지 않는다(아래 "보류" 참고).

1. URL 정규화 → 같은 공고면 기존 항목을 연다 (같은 URL 10회 등록해도 1건).
2. worker 작업으로 가져온다: HTTP 우선, 본문이 비어 있으면(동적 페이지) 격리된 headless 브라우저로 렌더링한다. 사설망·메타데이터 주소 차단(SSRF), 시간·크기 상한, 로그인 쿠키 미사용.
3. 항목 추출: 페이지의 구조화 데이터(schema.org `JobPosting`) → 알려진 채용 시스템 어댑터 → LLM 추출. 항목마다 원문 근거 위치를 남기고, 원문에 없는 값(예: 마감 시각)은 비워 `needs_review`로 둔다. 이미지 공고는 허용된 OCR을 쓴다(전송 정책 검사).
4. 사용자가 추출 결과를 확인·수정해 확정한다. 확정한 공고만 저장 공고가 된다.
5. 스냅샷: 정리 본문 + 페이지 스크린샷을 함께 보관한다. 실제 지원하면 그 시점 스냅샷을 제출 문서와 함께 고정한다.
6. 사용자가 "다시 가져오기"를 누르면 같은 과정으로 새 버전을 만들고, 내용 해시가 같으면 버전을 늘리지 않는다. 마감·문항·요건이 바뀌면 영향받는 초안을 표시한다.
7. 가져오기 실패는 `source_unavailable`, `login_required`, `rate_limited`, `needs_manual_check`로 표시하고 마감으로 처리하지 않는다. 대안으로 본문 직접 붙여넣기, 캡처 이미지·PDF 업로드, 내 브라우저에서 보내기(아래, c0043)를 제공한다.
8. 생애주기 (2026-11-17): 마감과 함께 **접수 시작**(`opens_at`)을 항목으로 둔다 — 원문(구조화 데이터·인용)에 적혀 있을 때만, 게시일에서 추측하지 않는다. 목록·상세는 공간 시간대로 접수 상태(`upcoming` 접수 예정 · `open` 접수 중 · `always` 상시 · `closed` 마감 · `unknown` 마감일 모름)와 채용 시기(상반기 1–6월·하반기 7–12월, 마감 → 접수 시작 → 저장한 날)를 계산하고(저장하지 않는다), 공고마다 지원 요약(지원 전 · 문항 n/m · 제출함 · 지금 전형 단계)을 붙인다. 공고 화면은 접수 상태로 나누고(입력 상태 "확인 필요"는 목록 위 한 줄, 보관은 맨 아래), 저장한 공고에서 바로 "지원서 쓰기". 지원 현황은 지원이 있는 것만(준비 중 → 제출 → 전형 중 → 결과) — 지원 전 공고는 공고 화면에만 둔다. 자세한 규칙: [postings.md](postings.md#접수-시작접수-상태채용-시기).

확정한 공고에서 준비 항목을 만든다(O09와 연결): 미충족·확인 필요 요건 → 학습 항목 또는 경험 확인 질문, 자소서 문항 → 문항별 작성 칸(글자 수 기준 포함), 전형 절차 → 시험 준비 항목, 일정 → 오늘 화면 D-day. 저장한 공고들 사이의 요건 빈도("저장 공고 20개 중 14개가 Docker 요구")는 사용자 저장분 기준임을 표시한다.

포털 전용 수집기는 오픈소스에 포함하지 않는다. 국내에서 채용 포털 간 대량 수집이 데이터베이스 제작자 권리 침해로 판단된 사례가 있다.

### 내 브라우저에서 보내기 (c0043)

로그인해야 보이거나 스크립트로 그리는 공고(사람인·잡코리아·원티드 등)와 참고 글은 서버가 가져오지 못한다. 서버는 로그인 쿠키를 쓰지 않는다(위 2번). 대신 사용자가 **자기 브라우저에서 보고 있는 페이지**를 보낸다. 사용자가 그 페이지를 열고 누를 때 한 건만 보내므로 위 수집 원칙과 같다.

1. 북마크 "브레인으로 보내기"(연결·관리 › 설정에서 끌어다 둔다, 이 앱 주소로 만든다). 누르면 이 앱의 `/capture`를 새 창으로 열고, 그 창이 준비됨을 알리면 페이지 주소·제목·선택한 글·HTML(2,000,000자에서 자름)을 `postMessage`로 **이 앱 주소에만** 한 번 보낸다. 그 사이트에는 토큰·쿠키를 두지 않고, API는 다른 출처에 열지 않는다(CORS 없음).
2. `/capture`는 받은 것을 믿지 않는다. HTML을 그리지 않고 DOMParser 문서에서 본문만 골라(Defuddle, MIT) Markdown으로 바꿔(Turndown, MIT) 글자로만 미리 본다(제목·사이트·앞부분·글자 수). 준비됨을 알린 뒤, 연 창에서 온, 정한 모양의, 페이지 주소의 출처가 보낸 창과 같은 메시지 하나만 받는다. 저장을 누르기 전에는 아무것도 넣지 않는다.
3. 공고로 저장 → `POST /core/job-postings/capture`: 받은 HTML을 서버가 같은 표준 라이브러리 파서로 고르고 같은 추출(채용 시스템 페이지 어댑터 → JSON-LD → LLM 인용 확인)·버전 규칙(본문 해시)을 탄다. 아무 주소에도 요청하지 않는다(공개 API 어댑터·브라우저 렌더링도 부르지 않는다). 버전 `method = browser_capture`, 화면에 "내 브라우저에서 가져옴". 로그인한 화면일 수 있어 모델에는 `private` 등급으로 보낸다. 선택한 글이 있으면 그것이 본문이다.
4. 브레인에 넣기 → `POST /core/sources/capture`: Markdown 원본(`text/markdown`, 앞에 제목·출처 줄)으로 넣고 원래 주소는 `sources.origin_url`. 참고 자료가 기본, 내 경험 자료도 된다. 증빙은 받지 않는다(웹 페이지는 증빙 서류가 아니다). 참고 자료는 늘 그렇듯 근거가 되지 않는다.
5. 휴대폰: 웹 앱 manifest의 `share_target`(GET `/capture?title=&text=&url=`, 안드로이드 Chrome에 설치했을 때). 주소만 공유하면 공고로 저장해 서버가 가져오고(위 1차 범위), 글을 공유하면 브레인에 넣기로 간다. 화면은 곧바로 주소창에서 쿼리를 지우고, `personal-api serve`의 접속 기록은 `/capture`의 쿼리를 남기지 않는다.

자세한 규칙과 보안 메모: [postings.md](postings.md#내-브라우저에서-보내기-c0043), [web.md](web.md#보고-있는-페이지-보내기-capture-c0043).

진행 (2026-11-17, c0043): 위 1–5 구현. 북마크·`/capture`·manifest(`share_target`), `POST /core/job-postings/capture`·`POST /core/sources/capture`, `job_posting_versions.method`에 `browser_capture`, `sources.origin_url`. 시험 `packages/core/tests/test_browser_capture.py`(가져오기 0건, private 등급, 같은 본문 버전 없음, 선택한 글, 목록 페이지, 상한, 모델 오류, 공간 분리, 증빙 거부·참고는 근거 아님, HTTP). 브라우저 확장은 하지 않았다(나중 선택지).

### 보류: 공고 자동화

아래 관심 조건·후보 발견·주기 재확인 흐름은 추가 검토 후 설계를 확정한다. 보고 있는 화면을 저장하는 방식은 북마크·휴대폰 공유로 만들었다 (위 "내 브라우저에서 보내기"). 브라우저 확장은 나중 선택지로 둔다.

#### 관심 설정 (보류)

회사를 지정하는 방식, 직무·조건으로 검색하는 방식을 URL 저장에 더해 지원하는 안이다.

설정 예시(실측·상품 한도가 아니라 편집 가능한 초기 기본값):

```yaml
watchlist:
  name: AI 서비스 개발 지원
  company_ids: [사용자가_선택한_회사]
  role_keywords: [백엔드, AI 서비스, Python]
  career_levels: [신입, 주니어]
  locations: [사용자_선택]
  sources: [등록한_공식_채용페이지, 허용된_검색원]
  check_interval_hours: 24
  max_candidates_per_run: 20
  keep_candidates_days: 7
  auto_pin: false
  on_unknown_requirement: needs_review
```

#### 처리 순서 (보류)

1. 활성 관심 조건만 읽는다.
2. 검색·RSS·공식 목록 등 가능한 경로에서 제목·링크·기본 조건을 먼저 확인한다.
3. 명확한 조건 불일치는 본문을 영구 저장하지 않는다. 미확인 조건은 탈락으로 단정하지 않는다.
4. 필요한 후보만 상세 페이지를 가져와 중복·기간·요건을 검사한다.
5. 적합 후보는 추천 보관함에 짧게 저장하고, 사용자가 저장하거나 미리 승인한 규칙을 충족한 것만 영구 목록으로 전환한다.
6. 같은 공고는 정규 URL·원본 식별자로 묶고 내용 해시가 달라진 경우만 의미 있는 버전을 추가한다.
7. 정기 실행은 변경 내역만 알린다. 변화가 없으면 문서나 알림을 다시 만들지 않는다.

ETag·Last-Modified를 제공하는 출처에는 조건부 요청을 적용한다. 지원하지 않는 출처에서는 정규화된 본문의 해시와 주요 필드를 비교한다. 동적 배너·조회 수·현재 시각 변경만으로 재분석하지 않는다. [S7]

### 보존 규칙

| 대상 | 기본 제안 |
|---|---|
| 관심 없는 검색 결과 (보류 기능) | 본문 저장 안 함, 필요 시 짧은 중복 방지 식별자만 |
| 아직 저장하지 않은 추천 후보 (보류 기능) | 7일 후 정리 |
| 가져왔지만 확정하지 않은 URL | 7일 후 정리 |
| 사용자가 저장한 공고 | 사용자가 삭제할 때까지 핵심 본문·요건 유지 |
| 저장 공고의 일반 변경 이력 | 의미 있는 변경만 압축 저장, 오래된 중간본 정리 가능 |
| 실제 지원한 공고 | 지원 당시 스냅샷을 제출 문서와 함께 고정 |
| 수집 HTML·스크린샷·중간 이미지 | 검증용 단기 보존, 필요한 증빙만 별도 고정 |
| 종료한 관심 목록 (보류 기능) | 주기 수집 중지, 기존 저장 자료는 유지 |
| 기업·업계 자료 | 관심 범위 내 요약·출처·필요한 원문만 저장 |

과거 공고를 사용자가 가져오면 저장할 수 있다. 과거 자료를 배제하는 정책과 전체 시장 수집을 하지 않는 정책은 다르다.

용량 계산 예시: 공고 500개 × 정리된 본문 30KiB × 2벌 = 약 29.3MiB. 이는 단순 계산이며 이미지·PDF·DB 오버헤드·색인·백업을 제외한다. 실제 용량은 업로드 자료와 OCR 이미지·버전 보존 정책을 측정해야 한다.

## 9. 문서 파싱과 근거 적재

`업로드 → 안전 검사 → 전송 정책 → 로컬 기본 추출/외부 파서 → 결과 정규화 → 품질 검사 → 검색·경험 후보`

- 같은 공간 안에서 파일 해시·파서·모델·옵션이 같으면 재처리를 피한다.
- 외부 파서에는 승인된 자료만 보낸다. 파서 실패 시 다른 제공자로 자동 전환하는 것도 추가 전송이므로 정책을 다시 검사한다.
- provider_job_id를 저장하고 제출 후에는 상태 조회 작업으로 분리한다. 긴 HTTP 연결이나 DB 트랜잭션을 붙잡지 않는다.
- 모델·페이지 한도는 계정 설정으로 관리한다. 무료 한도를 상수나 영구 보장으로 취급하지 않는다.
- Markdown·구조 JSON·원본 페이지 매핑을 보관한다. 없는 좌표나 인식 신뢰도를 만들어 넣지 않는다.
- 요청한 페이지 범위와 반환된 범위를 비교하고 부분 완료를 표시한다.
- 원격 ZIP·HTML·이미지도 신뢰하지 않는다. 경로 탈출·과도한 압축 해제·스크립트 실행을 막는다.
- API 키·서명 URL을 로그·모델 프롬프트·브라우저에 노출하지 않는다.

**글자 읽기(OCR)는 사용자가 고르지 않는다 (c0039, 2026-11-17).** 사진·스캔은 넣으면 앱이 읽는 길을 정한다.

- 증빙(또는 증빙일 수 있는 사진) → **이 기기에서** 읽는다: 브라우저의 tesseract.js(Apache-2.0, 한국어+영어 `4.0.0_best_int`). 엔진·학습 데이터는 이 앱이 정적 파일(`/ocr/*`, 빌드가 node_modules에서 복사)로 내주고, 처음 사진을 읽을 때만 받는다. 실행 중 CDN에 가지 않는다. 주민등록번호는 올리기 전에 브라우저가 `******-*******`로 가리고 서버가 한 번 더 가린다. 원본 그림 바이트는 그대로 둔다. 가린 수는 `parse_runs.text_layer.masked_resident_numbers`에 남아 "주민등록번호 보임" 표시가 유지된다.
- 증빙이 아닌 사진 → 연결된 모델이 그 자료 등급을 받으면(명시 라우트 `source_ocr`, 없으면 `job_extract_image`) 서버 worker가 모델로 읽고(`origin = model_ocr:<endpoint>`, 모델 장부 purpose `source_ocr`), 아니면 이 기기에서 읽는다. 확인 전(`purpose_pending`)·증빙 원본은 이 길로 가지 않는다.
- 글자 층: `PUT /core/sources/{id}/text-layer`(또는 올릴 때 form `text_layer`)로 쪽·글·위치(`bbox`)를 받아 `document_blocks(origin = device_ocr)`로 둔다. 같은 규칙으로 검사(블록 2000개·블록 2만 자·합 20만 자·300쪽·좌표 0–100000, 사진·PDF만, 엔진 이름 필수)하고, 다시 보내면 쌓지 않고 바꾼다. 로컬 글이 있는 쪽은 받지 않는다(`already_has_text`). 끝난 읽기에 붙으면 상태·빠진 쪽을 다시 계산하고 색인·증빙 항목 추출을 다시 건다.
- 스캔 PDF는 아직 브라우저에서 쪽을 그리지 않는다(pdf.js 미도입): 서버가 글을 못 찾으면 "쪽 사진으로 넣어 주세요"라고 알린다. 서버 쪽 붙이기(PDF, 읽기가 끝난 뒤)는 이미 받는다.
- 나중에 전용 OCR 연결(로컬 서버·사내 OCR)을 붙일 자리는 `ParserProvider` 포트다(`origin = provider:<name>`, 같은 빠진 쪽 계산). 화면 표시는 `read_by`: `device`("이 기기에서 읽음")·`model`("연결된 모델로 읽음")·`provider`·`local`.

## 10. 검색과 지식 연결

초기 검색은 PostgreSQL 안에서 끝낸다. 구조화 조건과 공간 권한으로 범위를 좁힌 뒤 제목·별칭·본문 검색과 pgvector 의미 검색을 결합한다. 한국어 동의어·복합어·띄어쓰기 샘플을 별도 시험한다. pg_trgm은 유사 문자열 보조이며 한국어 의미 검색의 대체로 취급하지 않는다. [S8]

임베딩은 OpenAI API와 로컬 모델(fastembed) 둘 다 같은 게이트웨이로 붙는다. 예시 설정의 기본은 OpenAI `text-embedding-3-large` 1024차원이고, 키가 없거나 라우트를 지우면 키워드 검색만 한다. 측정과 선택 근거: `docs/architecture/search.md`.

작은 개인 자료에는 정확 벡터 검색부터 측정한다. pgvector는 정확 검색과 근사 검색을 모두 지원하므로, HNSW 색인을 무조건 켜는 대신 부하 결과와 검색 재현율을 보고 추가한다. 임베딩 모델과 차원이 다른 자료를 같은 검색 공간으로 섞지 않는다. [S3]

공고 제목·일정 같은 구조화 값은 벡터화하지 않아도 된다. 상세 경험 연결이 필요한 저장 공고만 선택적으로 임베딩한다. 읽지 않을 추천 후보마다 LLM 요약·벡터를 만들지 않는다.

관계는 `요구함 / 학습함 / 적용함 / 입증함 / 보완필요` 등 명시적인 의미와 근거를 가진다. LightRAG나 별도 그래프 엔진은 기본 의존성이 아니다. 향후 같은 평가 세트에서 이득이 확인되면 SearchProvider 뒤에 추가한다.

## 11. 문서 수정·확정·제출본

문서는 구조화된 JSON을 원장으로 두고 블록에 안정적인 ID를 붙인다. Markdown·HTML·PDF·DOCX는 출력 형태다. 처음부터 두 방향의 무손실 변환을 모든 포맷에 약속하지 않는다.

수정 요청은 `artifact_id`, `base_revision`, `operations`, `evidence_ids`, `reason`, `idempotency_key`를 포함한다. 최신 버전이 다르면 409 충돌을 반환하고 자동 덮어쓰지 않는다. 적용된 초안은 새 버전으로 저장한다.

검증 대상은 이름·회사·기간·문항·글자/바이트 제한·원본 근거·문서 간 불일치다. AI 생성 문장은 원천 경력 근거로 재등록하지 않는다. 공개·제출 전에 민감 정보와 회사 기밀을 다시 검사한다.

승인에는 행위·대상·내용 해시·문서 버전·만료 시각·승인자·멱등 키를 묶는다. AI는 승인을 요청할 수 있지만 스스로 인간 승인을 생성할 수 없다. 승인 후 내용이 바뀌면 재승인이 필요하다.

실제 제출본은 당시 공고 버전과 함께 불변으로 남긴다. 이후 경력 수정은 다음 초안에 반영하며 이미 제출한 문서를 소급 변경하지 않는다. 면접 준비도 실제 제출본을 기준으로 시작한다.

### AI slop 방지 원칙

이 제품의 가치는 글 생성이 아니다. 경력의 깊은 정리, 공고와 경험의 근거 연결, 사실 검증, 면접·시험 준비가 가치다. 공고를 넣으면 자소서를 써 주는 기능은 범용 모델로 누구나 할 수 있고, 사용자 간 구별되지 않는 문장과 면접에서 방어할 수 없는 문서를 만든다.

1. **재료는 사용자에게서 나온다.** AI는 초안을 먼저 쓰지 않는다. 경험 정리는 인터뷰형 질문으로 시작한다. 본인이 한 일, 수치 결과, 선택 이유와 대안, 어려웠던 지점, 팀 성과와 본인 기여의 구분을 묻는다. 답은 근거가 연결된 경험 카드(claim + evidence)로 저장한다.
2. **근거 없는 문장은 경고한다.** 문서 문장은 artifact_claims로 브레인의 claim에 연결한다. 연결이 없는 경험·수치·역할 서술은 검증 경고 대상이다. AI가 빈칸을 그럴듯한 내용으로 채우지 않고 사용자에게 질문한다.
3. **범용 문장을 검출한다.** `artifact_validate`는 맞춤법보다 다음을 우선한다.
   - 회사 바꿔치기 시험: 회사명·직무명을 다른 값으로 바꿔도 성립하는 문장을 범용 문장으로 표시한다.
   - 구체성: 고유명사·수치·결정 이유·본인 행동이 없는 문단을 표시한다.
   - 상투어: 사용자가 편집 가능한 상투 표현 목록.
   - 다른 회사명 잔존: 이전 지원 문서를 복사하고 남은 회사·직무명.
4. **사용자 문장을 최소 수정한다.** AI 수정은 `artifact_propose_patch`의 제안으로만 하고 이유와 원문을 함께 보인다. 사실을 바꾸는 수정(참여→주도, 수치 확대)은 거부한다. 문서별로 사용자 작성분과 AI 수정분의 비율을 표시한다.
5. **쓰기 전에 지원 여부를 판단한다.** 공고 비교에서 미충족 요건이 많으면 작성 전에 보완·학습 또는 보류를 제안한다. 대량 지원·자동 지원은 기본 기능이 아니다.
6. **면접으로 역검증한다.** 제출본에서 예상 면접 질문을 만들고, 사용자가 답하지 못하는 문장을 제거 후보로 표시한다.
7. **결과를 기록하되 단정하지 않는다.** 서류·면접 결과를 문서 버전과 연결해 기록한다. 개인 단위 표본은 작으므로 원인 판단을 자동으로 확정하지 않는다.

스킬도 이 원칙을 따른다. `career-record`는 질문하는 절차를 중심으로 하고, `prepare-application`의 첫 규칙은 "AI가 먼저 쓰지 않는다"이다. 글자 수·바이트 수는 모델이 세지 않고 `artifact_validate` 결과만 사용한다.

### 요건 가시성 검사

채용 시스템은 파일 파싱, 필수 조건 확인, 공고 대비 점수화 또는 LLM 요약·순위화를 수행할 수 있다. 회사별 시스템과 기준은 공개되지 않으므로 특정 시스템이나 모델을 겨냥해 최적화하지 않는다. 목표는 사람과 기계 모두가 실제 적합성의 근거를 찾기 쉬운 문서다.

**기계 판독성 검사**: 핵심 내용의 표·이미지 의존, 비표준 섹션 이름, 모호한 날짜 형식, 공고 용어와 다른 기술명 표기(실제 사용한 기술에 한해 공고 표기를 병기하도록 제안).

**공고·문서·브레인 3자 비교**: 공고 요건마다 "이 문서만 읽었을 때 요건 충족의 명시적 근거가 있는가"를 판정하고 브레인의 근거와 겹쳐 본다.

| 브레인 근거 | 문서에 보임 | 판정 | 제안 |
|---|---|---|---|
| 있음 | 보임 | 충족 표시됨 | 유지 |
| 있음 | 안 보임 | 누락 | 해당 경험을 문서에 드러냄 |
| 없음 | 주장함 | 과장 위험 | 근거 추가 또는 문장 삭제 |
| 없음 | 없음 | 미충족 | 학습 보완 또는 지원 재검토 |

- 판정은 모델 게이트웨이(`ModelClient`) 뒤의 교체 가능한 판정 모델이 수행한다. 요건별 예/아니오 확률이나 점수를 정해진 형태로 돌려주는 모델(예: TypeSafe Jev)이나 범용 LLM(예: Gemini, Claude)을 쓸 수 있다. 한국어 공고·이력서에서의 정확도와 비용은 합성 평가 세트로 확인한 뒤 채택한다.
- 판정 모델은 대리 심사관일 뿐이다. 판정 모델의 점수를 올리는 것 자체를 목표로 삼지 않는다.
- 판정 확률은 "근거가 문서에 보이는가"에 대한 값이다. 합격 확률로 표시하지 않는다.
- 보유하지 않은 기술의 키워드 삽입, 숨김 텍스트, 심사 모델을 향한 지시문(프롬프트 인젝션)은 생성·제안하지 않는다. 문서에 그런 내용이 있으면 검증 경고로 표시한다.

## 12. AI·MCP·스킬·브라우저

### 모델 게이트웨이와 비용

모든 LLM 호출은 `career_core.llm.gateway.ModelGateway` 한 곳을 지난다. 순서는 라우트(용도 → 엔드포인트/모델) → 자료 등급 egress → 단가 확인 → 월 예산 → 호출 → 비용 계산 → 장부(`core.model_calls`) 기록이다. 상세: `docs/architecture/models.md`.

- 제공자: Anthropic(공식 SDK) 하나와 OpenAI 호환 Chat Completions(공식 `openai` SDK) 하나로 OpenAI·Gemini·xAI(Grok)·OpenRouter·Ollama·CLIProxyAPI 같은 프록시까지 붙인다. 설정은 `models.toml`(키는 환경변수 이름만).
- 단가: 제공자 공식 가격 페이지에서 옮긴 `catalog.toml`(항목별 출처·확인일·장문 구간·예고된 가격 변경). 응답에 실제 청구액을 주는 제공자(xAI)는 그 값을 우선한다. 모르면 비용은 0이 아니라 "미상"이고, 기본 설정에서는 단가 미상 종량제 모델을 호출하지 않는다.
- 구독 프록시(CLIProxyAPI 등)는 토큰만 기록하고 실지출로 세지 않는다. 원하면 API 정가 환산액을 따로 보여준다. 소비자 구독을 API처럼 쓰는 것은 제공자 약관 위반일 수 있음을 설정 예시에 적는다.
- 모니터링: `GET /api/core/usage`(일·모델·용도·엔드포인트·상태별), `personal-api usage`, `personal-api pricing`(오래된 단가·곧 바뀌는 단가·단가 없는 라우트, xAI 공식 단가 API와 대조). 대시보드 "시스템" 화면이 같은 API를 쓴다.
- 장부에는 프롬프트·응답 본문을 남기지 않는다. 앱 role은 INSERT/SELECT만 가진다.

### 호출 경로

```text
웹 작업 → REST → UseCase
외부 AI → MCP  → 같은 UseCase
예약 작업 → worker → 같은 UseCase
```

MCP는 모든 REST endpoint를 자동 노출하지 않고 업무 단위 도구만 제공한다. FastMCP는 FastAPI 안에 마운트할 수 있지만, 공식 문서도 무분별한 API 자동 변환보다 선별된 도구 설계를 권한다. [S9]

| 도구 예시 | 핵심 입력 | 결과·안전 조건 |
|---|---|---|
| brain_search | query, goal_id, filters | 권한 있는 근거만 반환 |
| evidence_get | source_span_id | 허용된 범위·원본 위치 |
| watchlist_upsert (보류) | 관심 조건, 출처, 주기 | 공고 자동화 확정 후. 정기 실행 등록은 사용자 승인 범위 |
| job_save | URL 또는 검증 자료 | 원문·확인일·미확인 항목 |
| job_compare_profile | job_id, goal_id | 충족·불충족·확인필요, 합격률 조작 금지 |
| artifact_get | artifact_id | 현재 revision·허용된 본문 |
| artifact_propose_patch | base_revision, operations, evidence | 초안 수정안 |
| artifact_validate | artifact_id, revision | 사실·형식 검증 결과 |
| approval_request | action, target, payload_hash | 승인 요청 ID, 승인 자체 아님 |
| run_start / run_status / run_cancel | workflow, input / run_id | 비동기 작업 ID·상태 |
| study_record_attempt | study_item_id, answer, result | 학습 기록, 실무 경험으로 전환 금지 |

원격 MCP는 OAuth 등 표준 인증으로 사용자와 도구 권한을 검증한다. 모델이 전달한 workspace_id를 신뢰하지 않는다. 토큰 대상·유효기간·권한을 검증하고 외부 토큰을 무검증으로 그대로 전달하지 않는다. 로컬 stdio 연결은 별도 어댑터로 제공할 수 있다. [S10]

기본 스킬은 `career-record`, `watch-jobs`, `prepare-application`, `study-assessment` 네 묶음으로 시작한다. SKILL.md와 예제·템플릿을 제공하지만 실행 권한은 서버에서 검사한다. 스킬/호스트의 지원 기능을 선언하고 검증한 조합만 배포한다. [S11, S12]

자체 실행에는 작업 큐와 필요한 LangGraph 체크포인트를 사용한다. 단순 fetch·OCR 조회는 일반 작업으로 충분하다. LangGraph의 실행 상태는 개인 사실의 원장이 아니다. [S13]

브라우저는 HTTP·공식 API로 해결되지 않는 동적 페이지에만 사용한다. 기본은 공개 정보 수집이며 개인 로그인 쿠키와 비밀 자료를 주지 않는다. Playwright MCP의 도메인 제한은 보안 격리의 대체가 아니므로 네트워크·파일·실행 권한을 별도로 제한한다. [S14]

임의 코드 실행·무제한 shell·임의 SQL 도구를 노출하지 않는다. 코딩 연습의 실행 채점은 격리 환경을 검증하기 전까지 외부 연습 도구 연결과 코드 분석으로 제공한다. 채용시험 대리 응시는 지원하지 않는다.

## 13. 개인 대시보드

원칙: 대시보드는 "오늘 무엇을 해야 하는가"로 이어져야 한다. 숫자 카드를 나열하지 않고, 상세 정보는 클릭 시 옆 패널로 연다.

메뉴는 **오늘 · 공고 · 지원 · 브레인 · 학습**, 아래에 작은 "도구"(사진 변환·숨김 글 검사)와 **연결·관리**. 검색은 메뉴 대신 명령 팔레트(⌘K, 이동·할 일·근거에서 찾기)로 모은다. 자세한 것은 [web.md](web.md#메뉴와-명령-팔레트).

| 화면 | 구성 |
|---|---|
| 오늘 | 맨 위 `마감 임박 + 안 쓴 문항`, 그다음 `확인 대기`(추출 경험 확인, 공고 변경, 승인 요청). 학습·최근 변경은 아래. 숫자 카드 나열 방식은 쓰지 않는다 |

## 14. 기본 보안과 운영

개인용도 로그인·세션 만료·HTTPS·권한 검사가 있어야 한다. 로컬 전용 개발 모드와 인터넷 배포 모드를 분리하고 공개 주소에서는 개발 무인증 모드를 허용하지 않는다. 세션은 HttpOnly 쿠키를 기본으로 하고 CSRF·Origin·로그인 시도 제한·세션 폐기를 함께 적용한다.

모든 URL 입력은 SSRF·리다이렉트·사설망·메타데이터 주소를 검사한다. 파일 접근에는 MIME·크기·다운로드 권한·경로 정규화를 적용한다. 원문·세션·토큰은 로그에서 제외한다.

DB 앱 계정과 마이그레이션 계정은 분리한다. RLS는 추가 방어이며 앱 권한 검사도 유지한다. DB 소유자·슈퍼유저·BYPASSRLS의 우회를 고려한다. 작업 큐와 체크포인트 같은 라이브러리 테이블도 사용자 API로 직접 노출하지 않는다. [S15]

백업은 일관된 DB 백업과 원본 파일 manifest를 함께 보관하고 서버 밖 암호화 복사본을 둔다. 실행 중인 DB 데이터 폴더를 단순 복사하지 않는다. 복원 훈련으로 유효성을 확인한다. 백업에서 복원한 삭제 자료가 다시 노출되지 않도록 삭제 기록의 재적용 절차도 둔다.

## 15. 배포·버전·서비스 연동 계약

코어 패키지에는 공개 인터페이스·스키마·마이그레이션이 포함된다. 설치 앱은 `create_app()` 또는 명시적인 router 등록으로 코어를 조립한다. 기본 인증·전송·예산 정책은 외부에서 주입하되 빈 설정으로 모든 권한이 열리지 않게 한다.

개인 배포는 코어 migration과 personal identity migration을 적용한다. 서비스 배포는 같은 코어 migration과 서비스 migration을 적용한다. 각 테이블의 변경 권한은 소유 레포에만 있다. 하나의 배포 명령이 잠금을 얻고 정해진 순서로 수행하며, API 시작마다 자동으로 schema를 변경하지 않는다. Alembic의 브랜치·의존성을 활용할 수 있지만 복수의 임의 migration 실행기는 금지한다. [S16]

Python wheel·UI·TS client는 호환 조합을 manifest로 배포한다. 개발 중 editable install은 가능하나 배포는 고정 버전·해시를 사용한다. 서비스의 main branch 추적이나 운영 중 즉시 최신 업데이트는 하지 않는다.

내보내기는 manifest·원본·확정 경험·문서 버전·관심 설정·학습 기록을 포함한다. 키·세션·쿠키·서비스 결제정보는 제외한다. 가져오기는 dry-run, schema 호환 검사, 해시 검사, ID 재매핑, 중복 정책을 갖춘다. 개인↔서비스 양방향 상시 동기화는 이번 범위가 아니다.

- 공통 답변(`answer_assets`·`answer_asset_claims`·`answer_asset_uses`, c0042): 1분 자기소개·지원 동기 틀·성격 장단점·갈등 경험·실패 경험·입사 후 포부·기타. 근거는 확인한 사실만 잇는다(`claim_not_confirmed`). `POST /core/answer-assets/{id}/use`가 지원 문서 끝에 문단으로 더하거나(`base_revision` 필수, 오래되면 409) 새 문서를 만들고 쓴 곳을 남긴다. 아직 확인한 사실인 근거만 문단마다 붙인다. 글에 이 지원이 아닌 회사 이름(회사·별칭·공고 회사명)이 보이면 `company_mentions`로 알리고 막지 않는다(`dry_run`으로 미리 본다). 웹 `/brain/answers`(종류 필터) · `/brain/answers/{id}`(글·근거 칩·쓴 곳).
- 지난 제출본(`GET /core/submitted-documents`): 제출할 때 고정한 문서만, 회사·직무·문항·제출일·글자 수. 한 편을 열면 그때의 글과 근거(제출 당시 문장 복사본). "이 글로 시작"은 새 공통 답변(`…/to-answer`, 지금도 확인한 사실인 근거만 따라옴)이나 작성 중인 다른 지원 문서(`…/use`, 블록의 출처 표시 유지)로 복사하고, 글에 회사 이름이 보이면 알린다. 웹 `/brain/submissions`.
- 기본 문서: `/documents` 경로는 그대로, 화면 이름만 "기본 문서", 브레인 색인 "나 · 내 글"에서 연다.
- MCP 읽기 도구 `education_list`·`skills_overview`·`answer_asset_list`·`answer_asset_get`(모두 untrusted 표시). 내보내기 `schema_step` c0040·c0041·c0042, 학력·공통 답변 병합 키.
- 아직 없음: 공통 답변 글의 자동 다듬기(사람이 쓴다), 면접 준비(O16)에서 공통 답변 묶기, 학력의 이력서 구역 채우기(O17), 성적증명서에서 학점 뽑기.

개발 순서: career-brain(이 레포)을 먼저 완성한다. career-service는 완성된 career-brain을 참고해 이후에 개발하며, 두 레포를 동시에 개발하지 않는다.

## 17. 고정 회귀 시험

1. 다른 workspace의 파일 ID·claim ID·run ID로 조회/수정/내보내기를 요청해도 실패한다.
2. MCP에서 직접 요청해도 웹앱과 같은 정책이 적용된다.
3. 같은 URL을 10회 등록해도 공고가 중복 생성되지 않는다.
4. 동일 본문을 10회 다시 가져와도 버전·임베딩 수가 불필요하게 늘지 않는다.
5. 마감·문항·요건이 바뀌면 변경 필드와 영향받은 초안을 표시한다.
6. 사이트 접근 실패는 채용 마감으로 처리하지 않는다.
7. 금지 등급 자료의 OCR·LLM 전송을 거절한다.
8. 파싱 중 worker가 종료되어도 provider job을 조회하고 중복 제출을 최소화한다.
9. base_revision이 오래된 수정은 덮어쓰지 않는다.
10. 승인 후 문서·대상이 변경되면 기존 승인을 사용할 수 없다.
11. AI 생성 초안이 경력의 원천 증빙으로 확정되지 않는다.
12. 제출본은 이후 경력 수정에도 바뀌지 않는다.
13. 복원된 공간의 원본·관계·문서가 연결되어 있다.
14. 외부 API 한도 초과 시 자동 유료 전환 없이 대기·실패 사유를 표시한다.
15. 외부 자료에 있는 명령으로 다른 자료 전송·shell 실행이 발생하지 않는다.
16. 회사명만 바꿔도 성립하는 문장과 다른 회사명이 남은 문장이 검증 경고로 표시된다.
17. 브레인 근거가 없는 경험·수치 서술은 경고되고, AI 수정안이 사실(역할·수치)을 바꾸면 거부된다.
18. 요건 가시성 검사가 누락(근거 있음·문서에 없음)과 과장 위험(근거 없음·문서 주장)을 구분한다.
19. 키워드 삽입·숨김 텍스트·심사 모델 대상 지시문을 생성하지 않고, 문서에 있으면 경고한다.
20. 글자·바이트 수는 모델 출력이 아니라 문항 설정(공백·줄바꿈·인코딩 기준)에 따른 코드 계산 결과다.
21. 단가를 모르는 종량제 모델 호출과 월 예산을 넘긴 호출은 제공자에 보내기 전에 거부되고, 거부도 장부에 남는다.
22. 구독 프록시 호출은 실지출 합계와 예산에 들어가지 않는다.
23. AI 추출 주장 중 원문에서 인용을 찾지 못한 것은 저장되지 않고, 저장된 인용은 원문 블록의 해당 범위와 글자 단위로 같다.
24. 확인 권한(approve) 없는 사람이나 팀/본인 구분이 없는 주장은 확정 상태가 될 수 없다 (앱 규칙 + DB CHECK).
25. API 임베딩은 restricted 자료를 색인하지 않고, 모델·차원이 다른 벡터를 한 검색에 섞지 않으며, 고친 본문의 옛 벡터를 쓰지 않는다.

## 19. 다음 단계: 참고 지식·지원 준비·이력서·포트폴리오 (설계, 2026-11-17)

실사용 점검을 시작하며 정리한 사용 모델이다. 사용자는 취업 자료를 경험 저장소·마스터 이력서와 직무별 파생본·기업별 지원본·면접 준비 자료·참고 자료로 나눠 관리한다. 브레인은 내 경험만이 아니라 공고·회사 조사·다른 사람의 자기소개서 같은 **참고 지식**도 모은다. 공고가 들어오면 둘을 비춰 보고, 문항마다 어떤 경험을 쓰면 좋을지 근거와 함께 정리해 보여 준다. 글은 사람이 쓴다. 지원을 자동으로 끝내는 흐름이 아니다.

| 사용자가 하던 일 | 브레인 | 상태 |
|---|---|---|

### 원칙

1. **두 칸을 나눈다.** 내 경험(확인한 사실, `claims`)과 참고 지식(공고·회사·남의 글)은 다른 칸이다. 참고 지식은 주장이 되지 않고, 문서 근거(`document_claims`)로 연결할 수 없으며, 근거 없는 문장 검사에서 근거로 치지 않는다. 화면·검색·MCP 도구에서도 따로 보인다.
2. **남의 글은 구성과 관점만 참고한다.** 참고 자기소개서 문장을 내 문서로 옮기지 않는다. 수정안·초안 모델에는 참고 글 원문 대신 사람이 확인한 구조 메모(문단 구성, 소재 종류, 강조 역량)만 넣는다. 문서 검사는 참고 글과 많이 비슷한 문장을 "참고 글과 비슷함"으로 짚는다.
3. **모으는 것은 사람이다.** 포털 대량 수집은 하지 않는다 (§8). 사용자가 연 페이지 URL, 붙여넣은 글, 올린 파일, 그리고 선택으로 공식 공개 API만 쓴다.
4. **회사 정보에는 시점이 있다.** 재무는 회계 연도, 인재상·사업 소개는 확인한 날을 함께 저장한다. 오래된 값은 화면에 표시한다. 기준일을 모르면 추측하지 않고 비운다.
5. **고르는 것도 사람이다.** 지원 준비 문서는 후보와 이유를 보여 줄 뿐이다. 문항에 어떤 경험을 쓸지는 사람이 고르고, 본문 초안은 사람이 요청할 때만 만든다.

### 19.1 회사 조사 (O13)

- 엔터티: `companies`(이름·별칭·홈페이지·선택 식별자), `company_facts`(종류: 인재상·핵심 가치·주요 사업·제품·재무·조직 문화·최근 소식·채용 절차·기타 / 본문 / 출처는 `source_spans` 또는 URL과 가져온 시각 / 기준일 / 확인 상태). 공고는 `company_id`로 잇는다. 지금 공고의 회사 이름 문자열은 같은 이름끼리 묶자고 제안하고 사람이 확인한다.
- 입력: (a) 회사 소개·채용·IR 페이지 URL. 공고 가져오기와 같은 fetch 경로와 인용 규칙으로 항목 후보를 뽑는다. (b) 붙여넣기·파일(IR 자료, 기사). (c) 선택 어댑터: 금융감독원 OpenDART(기업 개황·주요 재무, 사용자 키 필요, 자료 등급 `public`). 약관과 호출 한도는 구현 때 확인한다.
- 화면: 회사 페이지(종류별 항목 목록, 기준일·가져온 날·출처, 이 회사 공고, 이 회사 지원 이력). 공고 화면에 회사 한 줄.
- 상태 (c0033): (a)·(b) 붙여넣기 구현. (b)의 파일과 (c) OpenDART는 나중 — 식별자 칸(`corp_code`)만 먼저 둔다.
- 완료 기준: §16 O13.

### 19.2 참고 자료 보관함 (O14)

- 엔터티: `references`(종류: 합격 자기소개서·다른 사람 자기소개서·면접 후기·직무 글·기타 / 회사·직무·연도 태그(선택) / 출처 메모 / 원본 연결), `reference_notes`(구조 메모: 문항, 문단 구성, 소재 종류, 강조 역량. AI 후보, 사람 확인).
- 원본은 `sources`를 다시 쓰되 용도(`purpose`: `experience` | `reference`)를 둔다. 참고 원본은 경험 추출 대상에서 빠진다 (지금은 모든 원본이 경험 추출 대상이다).
- 검색: 기본 검색은 내 경험만 본다. 참고 지식은 필터를 켜야 보이고, 결과에 "참고" 표시가 붙는다. MCP도 내 경험 도구와 이름을 나눈다 (`reference_search` 등).
- 개인정보: 남의 글 속 이름·연락처·학교 같은 식별 정보는 저장 전에 가리자고 제안한다. 내보내기 묶음에는 포함하되 참고 자료임을 표시한다.
- 상태 (c0035): 표 이름은 `reference_items`(SQL 예약어 `references`를 피함). 붙여넣기·올린 참고 자료에서 만들기, 개인정보 가리기(참고 글 본문), 구조 메모 후보·확인, 비슷함 점검, `reference_search`·`reference_get` 구현. 원본 파일 가리기는 나중.
- 완료 기준: §16 O14.

### 19.3 공고별 지원 준비 문서 (O15)

이 단계의 중심이다. 회사 조사(O13)와 참고 자료(O14)가 없으면 그 칸을 비운 채로 동작한다. 그래서 먼저 만든다.

- 입력: 공고 버전(요건, `application_questions`의 문항·글자 수, 없으면 사람이 문항 입력), 확인된 내 경험·주장, 회사 정보(있으면), 같은 회사·직무의 참고 구조 메모(있으면).
- 출력 (문항마다):
  - 문항이 묻는 것: 한두 줄 풀이.
  - 후보 경험 2~3개: 경험·주장, 원문 근거, 이 문항·요건·인재상과 이어지는 이유, 빈 곳(수치 없음, 본인 역할 불분명, 기간 모름).
  - 회사 쪽 연결: 관련 인재상·사업 항목과 출처.
  - 참고 구성: 참고 글의 구조 메모 (문장은 넣지 않음).
  - 글자 수 한도.
- 출력 (문서 전체): 요건 충족표(근거 있음 / 근거 약함 / 근거 없음 → 인터뷰(O04)·학습(O09)으로), 같은 경험을 여러 문항에 쓰는 경우 경고.
- 동작: 후보는 먼저 검색(키워드 + 의미)으로 좁히고, 모델은 그 안에서 고르고 이유를 쓴다. 후보 목록 밖의 경험 ID는 버린다. 사람이 문항마다 경험을 고르면 지원 문서에 문항별 틀(고른 경험과 근거가 연결된 빈 문단)을 만든다. 본문 초안은 기존 수정안 경로(§11, 근거 연결 규칙)로 사람이 요청할 때만 만든다.
- 저장: 준비 문서는 공고 버전과 쓴 경험의 버전에 묶인 산출물이다. 공고가 다시 저장되거나 경험이 바뀌면 "오래됨"으로 표시하고 다시 만들 수 있다. 모델 라우트는 `application_prep`(기본은 `default`), 호출마다 사용량을 기록한다.
- 완료 기준: §16 O15.
- 상태: 구현함 (c0037). 사람이 고른 경험의 빈 문단은 웹 편집기가 화면에만 둔다(글 없는 문단은 저장하지 않는 규칙 때문) — 고른 것은 준비 문서에 남아 다시 열면 다시 놓인다. 웹은 지원 화면이 작업대가 됐다. 자세한 것은 §16 진행 (O15).

### 19.4 면접 준비 (O16)

- 지원 하나에서 예상 질문을 만든다. 출처는 공고 요건, 제출본 문장, 회사 정보, 참고 면접 후기다. 질문마다 쓸 경험·근거를 붙이고 답변 메모는 사람이 쓴다. 1분 소개도 같은 꼴로 둔다.
- 답변은 지원을 넘어 다시 쓰는 자산(`answer_assets`)이다. 공통 질문(지원 동기, 갈등 경험 등)은 지원마다 새로 쓰지 않는다.
- 기존 인터뷰(O04)는 경험을 채우려는 질문이고, 이것은 면접 대비 질문이다. 화면·데이터를 나눈다.
- 완료 기준: §16 O16.

### 19.5 이력서 만들기 (O17)

참고한 제품: working.cv (2026-11-17 확인). 이력서를 프로필·경력·학력·교육·프로젝트·자격·수료·논문 구역으로 나눈다. 프로젝트에는 제목·유형·URL·기간·진행 중·설명(마크다운)·태그·이미지(3장, PDF에는 안 들어감)·"이력서에 표시"가 있다. 그 밖에 첫 이력서 체크리스트, 공개·비공개와 공유 링크, 조회 통계, 계정 내보내기, 범위를 나눈 MCP(읽기·편집·공개·삭제)가 있다. 구역 나누기와 입력 편의는 따른다. 다른 점은 **이력서가 브레인에서 나온다**는 것이다. 빈 칸을 새로 채우는 편집기가 아니다.

- 판본: 마스터 이력서 하나 → 직무별 판본 → 공고별 판본. 판본은 위 판본을 복사해 시작하고 출처(판본·revision)를 남긴다. 공용 문서 복사(O07)와 같은 규칙이다. 공고별 판본은 지원 준비 문서(O15)에서 고른 경험 순서를 쓸 수 있다.
- 구역: 프로필(이름, 한 줄 소개, 연락처, 링크, 사진), 경력, 학력·교육, 프로젝트, 기술, 자격·수료, 수상, 논문·발표, 대외활동. 구역 순서와 표시 여부는 판본마다 정한다.
- 항목 채우기: 경력·프로젝트 항목은 경험(`experiences`)을 고르면 기간·조직·역할이 들어온다. 성과 줄은 그 경험의 **확인된 주장** 중에서 고른다. 줄마다 근거가 연결된다. 사람이 직접 쓴 줄도 허용하지만 "근거 없음"으로 표시하고, 기존 문서 검사(범용 문장·근거 없는 문장)를 그대로 받는다. 줄 다듬기는 기존 수정안 경로(§11)로, 사람이 요청할 때만 한다.
- 사진: 사진 변환 도구(웹 `/tools/photo`)로 만든 결과를 프로필 사진으로 저장한다. 원본이 아니라 변환된 파일 하나만 보관하고 EXIF는 없다.
- 블라인드 모드: 판본마다 사진·생년월일·성별·출신 학교·가족 사항을 출력에서 뺀다. 공공기관 표준 이력서처럼 이런 항목을 받지 않는 지원에 쓴다. 공고 문항에 블라인드 안내가 있으면 켜자고 제안한다.
- 출력: 템플릿 2~3개(단정한 한 단, 두 단, 한국식 표 양식)와 A4 쪽 나눔 미리보기를 둔다. 1차 PDF는 웹 인쇄 화면(브라우저 "PDF로 저장", 인쇄용 CSS)이라 서버 의존성이 없다. DOCX·Markdown·HTML은 기존 문서 writer를 넓혀 쓴다. 서버에서 PDF를 만드는 렌더러는 선택 설치로, 뒤에 검토한다.
- 호환: JSON Resume 형식으로 가져오기·내보내기를 한다. 가져온 항목은 경험 후보로 들어가고 확인을 거친다(§9 규칙).
- 공개: 개인 설치에서 이력서를 공개 URL로 띄우지 않는다. 자기 서버를 인터넷에 여는 일이 되기 때문이다. 대신 정적 HTML 내보내기를 주고, 사용자가 원하는 곳에 직접 올린다. 공개 호스팅·공유 링크·조회 통계는 서비스(career-service)의 범위다.
- 체크리스트: working.cv의 첫 이력서 체크리스트처럼 비어 있는 필수 구역, 근거 없는 줄 수, 오래된 연락처, 쪽 수 초과를 판본 화면 위에 보여 준다.
- MCP: 읽기 도구와 판본 편집 도구를 나눈다. 편집은 웹과 같은 권한·승인 규칙을 따른다(O08).
- 완료 기준: §16 O17.

### 19.6 포트폴리오 (O18)

- 포트폴리오 항목은 경험 하나에 붙는다(`portfolio_items.experience_id`). 항목에는 링크(저장소·데모·글·영상), 이미지(스크린샷·구성도), 기술 태그, "문제 → 내 역할 → 한 일 → 결과" 구성이 있다. 결과 줄은 이력서처럼 확인된 주장에서 고르고, 직접 쓴 글은 표시한다.
- 이미지는 브라우저에서 긴 변·용량 한도로 줄인 뒤 올린다(사진 변환 도구의 처리 코드를 다시 쓴다). 원본 EXIF는 지운다. 이미지마다 "공개 가능 / 지원서에만 / 나만" 표시를 둔다. 회사 내부 화면이 섞이기 쉽기 때문이다.
- 가져오기: 공개 GitHub 저장소 URL에서 README·주 언어·만든 날·마지막 커밋을 가져와 원본으로 저장한다(경험 추출 대상). 토큰 없이 공개 API 호출 한도 안에서만 쓰고, 비공개 저장소는 사용자 토큰(선택)으로만 읽는다. 커밋 수 같은 숫자는 "본인 기여"의 근거로 쓰지 않는다. 기여는 사람이 확인한다.
- 묶음: 포트폴리오는 항목을 골라 순서를 정한 묶음이다(전체, 직무별, 공고별). 공고별 묶음은 O15에서 고른 경험부터 놓자고 제안한다.
- 출력: PDF(웹 인쇄 화면, 항목 하나에 한두 쪽, 표지·목차), 정적 HTML 묶음(이미지 포함, 서버 없이 열림), 이력서 프로젝트 구역에서 항목으로 가는 링크. "나만" 이미지와 비공개 항목은 어떤 출력에도 들어가지 않는다.
- 완료 기준: §16 O18.

## 20. 브레인 구조 다시 잡기 (설계, 2026-11-17)

실사용 점검에서 나온 지적이다. 지금 브레인은 경험 한 줄 목록과 "올린 자료"뿐이라 세 가지가 안 된다.

1. **많아지면 못 찾는다.** 경험에 종류·날짜·태그·상하 관계가 없다(`period_text` 원문뿐). 그래서 정렬·묶기·거르기를 할 수 없다.
2. **내 것과 남의 것이 섞인다.** 올린 자료는 모두 경험 추출 대상이다. §19 원칙 1(두 칸)이 화면과 데이터에 아직 없다.
3. **증빙을 둘 곳이 없다.** 증명사진·자격증·어학 성적표·수료증·졸업/경력증명서는 "경험"이 아니라 "사실 + 사본 파일"이다. 지금은 넣으면 주장 추출로 흘러가거나 넣을 곳이 없다.

### 구조

```
브레인
├─ 나 · 사실 (내 기록 · 근거로 쓸 수 있음)
│  ├─ 프로필          인적 사항, 연락처·링크, 증명사진(규격별), 병역·보훈·장애·희망 조건(선택, restricted)
│  ├─ 경험            경력 › 그 안의 프로젝트 / 개인 프로젝트 / 교육 / 대외활동
│  ├─ 학력            학교·전공·학위 과정·상태·기간·학점 (표, O23)
│  ├─ 자격·어학·수상  자격증, 어학, 수료, 수상 (표)
│  ├─ 기술            태그·확인한 사실·자격에서 모은 보기 (따로 적지 않음, O23)
│  └─ 증빙 서류       사본 파일, 발급일·만료일, 이어진 기록
├─ 나 · 내 글 (내가 쓴 글)
│  ├─ 기본 문서       지원마다 복사하는 이력서·포트폴리오 (/documents)
│  ├─ 공통 답변       1분 자기소개·지원 동기 틀 … 근거는 확인한 사실만 (O23)
│  └─ 지난 제출본     제출할 때 고정한 글, 읽기 전용 (O23)
├─ 참고 (남의 지식 · 근거로 못 씀)      회사(§19.1), 참고 글(§19.2)
└─ 받은 자료함    올린 파일·붙여넣기 → 용도를 정해 보낸다
```

공고·지원·학습은 지금처럼 따로 메뉴다. 공고는 일감이고, 학습은 "계획이지 경험이 아님"(O09)이기 때문이다.

### 규칙

- **용도가 처리를 정한다.** 올릴 때 용도를 고른다(파일 종류·내용으로 제안, 사람이 확정, 나중에 바꿀 수 있음).
  - 내 경험 자료 → 지금처럼 경험·주장 후보 추출.
  - 증빙 → 주장 추출 안 함. 항목(자격명·발급 기관·번호·취득일·만료일·점수)만 뽑아 자격·이수 기록 후보로. 로컬 파싱/OCR만 쓰고 외부 모델 전송은 하지 않는다(자료 등급 `restricted`).
  - 참고 → §19.2 규칙. 구조 메모만, 근거 연결 불가.
- **증빙 원본은 보존한다.** 제출할 때 사본을 그대로 다시 써야 하므로 BlobStore에 원본 바이트를 둔다(지금 원본과 같은 해시·중복 규칙). 주민등록번호 같은 식별 정보가 보이면 표시하고(§11 민감 정보 검사 재사용), 내보내기에는 포함하되 묶음 안에서 따로 표시한다.
- **자격·이수 기록**은 확인 상태를 가진다: `extracted`(파일에서 뽑음) / `self_confirmed` / `evidence_supported`(증빙 파일 연결). 이력서(O17)의 자격·수료·수상·학력 구역은 여기서 온다. 경험과 이을 수 있다(예: 부트캠프 수료 ↔ 그때 한 프로젝트).
- **만료가 일정이 된다.** 어학 성적(보통 2년)·자격 갱신일이 다가오면 오늘 화면 일정에 마감처럼 뜬다. 만료일을 모르면 추측하지 않는다.
- **증명사진**은 사진 변환 도구(`/tools/photo`)에서 "프로필에 저장"으로 넣는다. 규격(3×4, 반명함, 여권 3.5×4.5 등)별로 여러 장, 기본 하나. 변환본만 두고 원본·EXIF는 두지 않는다(§19.5).
- **찾기.**
  - 브레인 첫 화면은 목록이 아니라 색인이다: 묶음마다 수와 최근 항목, 맨 위에 "확인할 것"(추출 후보·증빙 항목 후보·곧 만료).
    - 구현(2026-11-17): 검색 상자 아래 두 칸 색인. "나"(프로필·경험·자격·이수·증빙 서류)와 "참고"(회사·참고 글)를 나란히, 줄마다 수와 손이 갈 표시(확인 필요·곧 만료·주민등록번호 보임)만. 그 아래 확인할 것 → 받은 자료함 → 경험 타임라인. 거름을 켜면 색인은 숨긴다.
    - O23: 세 칸 색인 "나 · 사실"(프로필·경험·학력·자격·어학·수상·기술·증빙 서류), "나 · 내 글"(기본 문서·공통 답변·지난 제출본), "참고"(회사·참고 글). 넓은 화면 세 칸, 중간 두 칸 + 한 칸, 좁은 화면 위아래. 진한 표시는 손이 갈 것만(확인 필요·곧 만료·주민등록번호 보임·학력으로 옮길 기록).
  - 브레인 안 검색 상자: 기본은 "나"만, "참고 포함"을 켜야 참고가 보이고 결과에 "참고" 표시.
  - 경험 목록: 연도별 연표(기본)와 표 보기. 종류·기간·조직·기술 태그·확인 상태로 거르고, 자주 쓰는 거름은 저장(`saved_views`). 경력 아래 프로젝트는 접어서 보인다.
  - 받은 자료함: 용도 미정·처리 실패·부분 추출만 위에. 다 처리된 자료는 기록 쪽에서 "원본"으로 찾아 들어간다(파일 목록이 중심 화면이 되지 않게, §13).

### 브레인에 넣기 (c0039, 2026-11-17)

실사용 지적: "OCR은 그냥 파일 넣는 걸 만들어야 하는 거 아닌가? 브레인에 때려박는 창이 있어야 하는데." 사용자는 OCR·용도·라우트를 생각하지 않는다.

- **창 하나.** 브레인의 "브레인에 넣기"(예전 "자료 올리기"): 파일 여러 개 끌어다 놓기·고르기, 글·주소 붙여넣기(주소는 한 줄에 하나), 화면 캡처 붙여넣기. 브레인 화면 어디에 파일을 놓아도 이 창이 열린다. 넣은 것마다 줄 하나: 무엇으로 보는지(내 경험 자료·증빙 서류·참고 자료 / 공고·회사 페이지)를 한 번 눌러 바꾸는 칩과 진행(기다리는 중 → 읽는 중 → 보내는 중 → 나누는 중 → 저장됨 / 확인 필요 / 실패 + 쉬운 이유). 창을 닫아도 처리는 이어진다(한 번에 셋).
- **고르기는 이 설치 안에서만.** `career_core.domain.ingest`의 규칙(파일 이름·형식·앞부분 글): 주민등록번호 꼴·"증명합니다"·수료증·성적증명·재직/졸업증명·TOEIC·OPIc → 증빙, 1인칭 글("저는", "제가", "담당했") → 내 경험, 남의 글·후기·회사 소개 → 참고. 외부 모델에 보내 고르지 않는다. 주소: 채용 사이트(사람인·잡코리아·원티드·점핏·Greenhouse·Lever·Workday·그리팅·나인하이어 …)·공고 꼴 경로 → 공고 저장, `about`·`company`·`ir`·`culture` → 회사 페이지(이 공간 회사의 홈페이지 호스트·이름과 맞추고, 없으면 이름을 받아 회사를 만든 뒤 가져온다). HTTP `POST /core/ingest/classify`(100개까지), `GET /core/ingest/capabilities`.
- **확신하면 바로, 아니면 묻는다.** 높은 확신이면 그 용도로 바로 보낸다(경험 자료는 설정에 따라 바로 경험 후보 뽑기). 낮으면 `sources.purpose_pending = true`·`purpose_hint`(이유 코드)로 저장하고 받은 자료함에 "확인 필요"로 제안을 미리 골라 둔다. 확인 전 자료는 `restricted`(DB CHECK `ck_sources_pending_restricted`)라 모델로 가지 않는다. 확인은 사람만(에이전트 `PATCH`는 용도를 바꿔도 확인 전으로 남는다). 내 경험으로 확인하면 등급을 `private`로 낮추고 경험 추출을 건다. 바로 보낸 자료는 받은 자료함에 나오지 않는다.
- 아직 없음: 브라우저 pdf.js 쪽 그리기, 사진·붙여넣은 글에서 공고 만들기, 주소의 "확인 필요"는 창 안에만(서버 받은 자료함에는 없음), 모델 OCR 비용 확인 문턱.

## 21. 연결·관리 (설계, 2026-11-17)

개인 설치는 사용자가 운영자다. 지금은 모델 연결이 `models.toml` + 환경변수뿐이라 웹에서 보거나 바꿀 수 없고, 관리 기능은 시스템·사용량·설정 세 메뉴에 흩어져 있다. 일상 화면(오늘·브레인·공고·지원·학습)과 관리 화면을 나누고, 관리 화면을 한 곳에 모은다. 작업을 막는 문제(키 없음, 예산 초과, 승인 대기)만 오늘 화면에 한 줄로 알린다.

### 모델 연결

연결 추가는 종류를 먼저 고른다. 종류마다 묻는 칸이 다르다.

| 종류 | preset | 묻는 것 | 과금 |
|---|---|---|---|
| 공식 API | anthropic · openai · gemini · xai · openrouter | API 키 | 종량제 (단가표, 월 예산) |
| 구독 계정 (CLIProxyAPI) | cliproxyapi | 프록시 주소(기본 `http://127.0.0.1:8317/v1`), 프록시 키, 환산 기준(`price_as`) | 구독 (실지출 0, 환산만) |
| LiteLLM 프록시 | openai-compatible | 주소(기본 `http://127.0.0.1:4000/v1`), 키, 과금 방식(종량제·구독), 단가 기준 | 고른 대로 |
| 로컬 모델 (Ollama) | ollama | 주소 | 무료 |
| 직접 (OpenAI 호환) | openai-compatible | 주소, 키, 과금, 토큰 파라미터 | 고른 대로 |

- **구독 계정 로그인은 프록시가 한다.** ChatGPT·Claude·Gemini 구독 OAuth를 이 앱이 직접 구현하지 않는다. 다른 CLI의 클라이언트 ID를 빌려 쓰는 일이 되고, 약관·보안 책임이 이 앱으로 넘어오기 때문이다. CLIProxyAPI(또는 LiteLLM)에서 로그인하고, 여기서는 그 주소와 키만 받는다. 화면에 "소비자 구독을 API처럼 쓰는 것은 제공자 약관에 어긋날 수 있다"를 그대로 적는다(§12).
- **보낼 수 있는 자료.** 연결마다 `public`·`private`을 고른다. 기본은 아무것도 아님(= 호출 거부). `restricted`는 고를 수 없다. 로컬 모델은 기계 밖으로 나가지 않는다고 표시한다.
- **연결 시험**은 과금되지 않는 `GET {base_url}/models`(Anthropic은 `GET /v1/models`)만 부른다. 응답의 모델 목록을 용도별 모델 고르기에 쓴다. 실제 생성 호출로 시험하는 것(`personal-api ping`)은 과금된다고 적고 따로 둔다.
- **키 저장.** 키는 DB에 암호화해 둔다(`cryptography` Fernet). 암호 키는 `CAREER_SECRET_KEY` 환경변수, 없으면 처음 쓸 때 데이터 폴더에 `secret.key`(권한 0600)를 만든다. API는 키를 돌려주지 않는다. 화면에는 "저장됨 · 끝 4자리"만. 내보내기 묶음에 키를 넣지 않는다(§11 내보내기 제외 규칙과 같음). 복원하면 연결은 남고 키는 "다시 넣어야 함"이 된다.
- **파일 설정과 함께 쓴다.** `models.toml`의 연결·라우트·예산은 그대로 읽고, 화면에는 "파일에서 옴 · 읽기 전용"으로 보인다. 화면에서 만든 연결은 DB에 둔다. 이름이 겹치면 화면 쪽 저장을 거부한다. 라우트·예산은 화면 값이 파일 값을 덮는다(덮은 것을 표시, "파일 값으로 되돌리기").
- **바꾸면 바로 쓴다.** 저장하면 API 프로세스의 게이트웨이 설정을 다시 만든다. 워커 프로세스는 호출 전에 설정 버전을 확인해(몇 초 간격) 바뀌었으면 다시 읽는다.
- **서비스에서는.** 이 기능은 개인 앱이 켤 때만 동작한다(주입 없으면 거부). 서비스는 운영자 설정을 쓰고, 사용자 자기 키 연결(BYOK)은 서비스가 따로 정한다. 테이블에는 처음부터 `workspace_id`가 있다.

### MCP·에이전트

MCP 서버는 이미 있다(O08, `docs/architecture/mcp.md`). 화면에 붙는 방법을 모은다.

- 클라이언트별 설정 조각: Claude Code(`claude mcp add --transport http …`), Codex(`config.toml`), Claude Desktop(stdio), Cursor. 서버 주소는 지금 화면이 붙은 주소로 채운다. 토큰 자리는 `<토큰>`으로 두고, 옆의 "에이전트용 토큰 만들기"가 권한(읽기·초안 쓰기 등)과 만료를 고르게 해 한 번만 보여 준다.
- 도구 목록과 권한: 어떤 도구가 어떤 권한을 요구하는지 표. AI는 승인하지 못한다는 규칙(§12)을 적는다.
- 호출 기록·원격 연결(OAuth): 지금 시스템 탭 그대로 옮긴다.

### API (core HTTP, 개인 앱이 켤 때)

| 메서드·경로 | 내용 |
|---|---|
| `GET /core/models/status` | 연결 목록(파일 + 화면, 출처 표시, 키 상태 `set`·`missing`·`not_needed`·`needs_reentry`, 끝 4자리), 라우트(출처), 예산(출처), 이번 달 실지출 |
| `POST /core/models/connections` | 연결 추가 `{name, preset, base_url?, api_key?, billing?, price_as?, data_classes[], token_param?}` |
| `PATCH /core/models/connections/{name}` | 고치기 (키는 보낼 때만 바뀜, `api_key: null`이면 지움) |
| `DELETE /core/models/connections/{name}` | 끊기 (쓰는 라우트가 있으면 409 `connection_in_use`) |
| `POST /core/models/connections/{name}/test` | `/models` 목록 시험, `{ok, models[], error_code?}` |
| `PUT /core/models/routes` | 용도별 라우트 덮기 `{routes: {purpose: "conn/model" \| null}}` (null = 파일 값으로) |
| `PUT /core/models/budget` | `{monthly_usd: "20.00" \| null}` |

권한: 읽기는 `read`, 바꾸기는 `workspace-admin`. MCP 도구로는 열지 않는다(키를 에이전트가 다루지 않게).

### 순서와 완료 기준

- **O22 연결·관리**: 위 전부. 완료 기준: 화면에서 만든 연결로 라우트를 돌리면 재시작 없이 호출됨, API 응답·로그·장부·내보내기에 키 값 0건, 다른 공간에서 연결 0건, `restricted` 선택 불가, 시험 호출은 과금 0, 옛 주소가 새 탭으로 감.
