# 개인 커리어 브레인 — 오픈소스 레포 구축 계획

작성 기준: 2026-11-16  
레포 가칭: `career-brain`  
상태: 설계 제안. 레포 생성·배포·성능 시험을 수행한 결과가 아니다.

## 1. 목표와 범위

개인이 자신의 서버에서 경력·프로젝트·학습·문서·관심 공고·지원 이력을 보관하고, 웹 대시보드와 AI 도구를 통해 관리하는 완결된 오픈소스를 만든다. 클라우드 서비스 가입이나 유료 라이선스 서버 없이 핵심 기능이 동작해야 한다. 외부 모델·OCR·검색 API 사용 비용은 소프트웨어의 무료 배포와 구분한다.

이 레포는 다음 두 역할을 함께 가진다.

1. 바로 설치해서 쓰는 개인용 제품: React 개인 대시보드, FastAPI 실행 앱, PostgreSQL, 작업 실행기, 설치·백업 도구.
2. 서비스 레포가 재사용하는 공통 엔진: Python 패키지, API 계약, 문서 편집·근거 표시용 UI 구성요소, MCP 도구, 업무 스킬.

공개 서비스의 마케팅 화면·회원 운영·결제·플랜·운영자 화면·운영용 배포 설정은 다른 레포에서 개발한다. 이 레포에 `IS_CLOUD` 분기를 계속 추가해 하나의 앱을 두 제품으로 억지 분기하지 않는다.

공고 전체를 긁어 오는 시스템은 범위 밖이다. 사용자가 정한 관심 기업·조건·저장 공고만 탐색·추적하며, 관심 없는 공고 본문은 영구 적재하지 않는다. 세컨드 브레인은 취업 자료에만 제한하지 않고 사용자가 직접 저장한 일반 지식·학습 자료도 수용한다.

## 2. 두 레포의 관계

```text
career-brain [공개]
  공통 엔진 + 개인용 API 실행 앱 + 개인 대시보드
  Python wheel / TypeScript 패키지 / 스킬 팩 배포
                         │ 버전 고정 의존성
                         ▼
career-service [기본 비공개]
  서비스 프론트 + 서비스 백엔드 + 회원·결제·운영
```

의존 방향은 서비스 → 공통 엔진 하나로 제한한다. 공개 레포가 비공개 모듈을 import하거나, 기본 실행에 서비스 전용 API를 요구해서는 안 된다. 서비스 레포에 코어 소스를 복사하지 않고 고정된 배포 패키지를 설치한다.

두 레포는 두 API 서버를 반드시 네트워크로 연결한다는 뜻이 아니다. 서비스 실행 앱은 코어를 라이브러리로 조립해 API 프로세스 하나로 실행할 수 있다. 개인용 API 실행 앱은 그 자체의 별도 설치 환경에서 실행한다. 개인용 DB와 서비스 DB도 별개이며 기본적으로 동기화하지 않는다.

## 3. 라이선스 방침

공통 엔진과 개인 대시보드는 Apache-2.0을 우선 제안한다. 서비스 백엔드가 공통 엔진을 직접 import하면서 자체 코드는 비공개로 유지하는 구성을 단순하게 하기 위한 선택이다. 고지·라이선스·NOTICE 등 원 라이선스의 조건은 준수한다. 기존에 검토한 AGPL 프로젝트 코드를 단순히 가져와 Apache-2.0으로 바꾸지 않는다. 외부 의존성·템플릿·모델·폰트·자료의 라이선스는 별도 목록으로 관리한다. [S1]

공개 저장소에 실제 개인정보, 회사 자료, 사용자 DB, 모델 키, 브라우저 쿠키, 운영 로그를 넣지 않는다. 데모는 합성 데이터를 사용한다. 저장소 공개 전 현재 파일뿐 아니라 Git 이력도 검사한다.

## 4. 레포 구조

```text
career-brain/
  apps/
    personal-web/                 # React + TypeScript + Vite + shadcn/ui
    personal-api/                 # FastAPI composition root, 개인 로그인·설정
  packages/
    core/
      pyproject.toml
      src/career_core/
        domain/                  # 업무 개념·상태·규칙
        usecases/                # 읽기·작성·확정·수집·학습의 공통 처리
        ports/                   # 외부 기능 인터페이스
        db/                      # SQLAlchemy 모델·저장소
        migrations/              # 코어 테이블의 Alembic revision
        adapters/                # pgvector·파일·OCR·모델·검색 연결
        workflows/               # 필요한 LangGraph 흐름
        jobs/                    # 작업 핸들러와 큐 어댑터
        interfaces/http/         # 공통 FastAPI routers
        interfaces/mcp/          # 선별한 MCP tools
    ui/                          # 문서 편집·변경 비교·근거 카드
    client/                      # 인증·기본 URL을 주입받는 TS 클라이언트
  contracts/                     # OpenAPI·JSON Schema·호환성 문서
  skills/                        # 업무 지침과 합성 예제
  deploy/compose/                # 개인용 compose·Caddy
  tests/{unit,integration,e2e,security,fixtures}/
  docs/{architecture,operations,contributing}/
```

`packages/core`에는 결제 SDK, 서비스 도메인, 광고 분석, 고객 지원 전용 로직을 넣지 않는다. `packages/ui`에는 앱 전체 네비게이션이나 SaaS 가입 흐름을 넣지 않는다.

## 5. 기본 기술과 실행 구조

- 프론트: React·TypeScript·Vite·shadcn/ui, 서버 상태는 TanStack Query, 폼과 검증은 일관된 스키마 기반으로 구성.
- 서버: FastAPI·Pydantic·SQLAlchemy·Alembic. 라우터는 요청 검증과 유스케이스 호출만 담당.
- DB: PostgreSQL, 의미 검색은 pgvector, 유사 문자열은 pg_trgm. 별도 OpenSearch·Neo4j·벡터 DB를 필수로 두지 않는다.
- 큐: Procrastinate를 `JobQueue` 어댑터 뒤에 배치. 주기 작업·재시도·잠금은 활용하되 교체 가능하게 한다. 해당 프로젝트는 유지보수자 모집도 안내하므로 버전과 운영 상태를 점검한다. [S2, S3]
- 문서 편집: Tiptap 오픈소스 코어. AI·버전·비교 기능은 우리의 코어와 UI로 구현하며 Pro 확장을 무료 기본 기능으로 가정하지 않는다. [S4]
- AI: 외부 모델 제공자 어댑터. MCP를 통한 외부 AI 호출은 모델 사용과 분리한다.
- 파싱: 가벼운 텍스트·HTML·문서 추출 우선. 복잡한 PDF·스캔 자료는 허용된 PaddleOCR·MinerU API. 로컬 OCR 모델 상시 실행은 기본 구성에 없다. [S5, S6]

```text
PC·모바일 → Caddy → personal-web 정적 파일
                    └→ personal-api → core usecases
                                         ├→ PostgreSQL
                                         ├→ 비공개 파일 볼륨
                                         └→ 작업 큐 → worker
외부 AI → 인증된 MCP → 동일한 core usecases
```

작은 서버에서는 `personal-api serve` 한 프로세스가 API·worker(별도 스레드)·웹 정적 파일을 함께 맡는다 (설치: `docs/operations/install.md`, 언어 선택 근거: `docs/architecture/rust.md`). 상시 컨테이너는 Caddy·API·PostgreSQL·worker를 기본으로 한다. 스케줄러는 worker 계열의 가벼운 루프로 실행하고 동일 주기 작업을 중복 등록하지 않도록 잠근다. 브라우저는 필요 작업에만 켜며 기본 웹 서비스와 분리된 권한으로 실행한다.

| 모듈 | 책임 | 금지할 결합 |
|---|---|---|
| Library | 원본·버전·문서 블록·근거 위치 | 원본을 즉시 확정 경력으로 취급 |
| Brain | 경력·경험·개념·목표·선호·관계 | AI 초안을 사실의 근거로 재사용 |
| Career | 관심 조건·회사·선택 공고·지원 전형 | 시장 전체 공고 저장 |
| Documents | 이력서·자소서·포트폴리오·수정안·제출본 | 브라우저 클릭에 의존한 자체 문서 수정 |
| Learning | 필요한 시험·학습·풀이·오답·복습 | 공개되지 않은 시험 내용을 사실로 확정 |

외부 연결은 `BlobStore`, `ParserProvider`, `ModelClient`(모델 게이트웨이 뒤), `SearchProvider`, `BrowserRunner`, `JobQueue`, `NotificationSink` 같은 작은 인터페이스로 제한한다. 모든 것을 플러그인으로 만드는 범용 프레임워크까지 만들지는 않는다.

## 7. 데이터 모델

사용자 데이터에는 처음부터 `workspace_id`를 둔다. 개인용에서는 기본 공간 하나를 사용하더라도 이를 전역 상수로 하드코딩하지 않는다. 작성자 식별은 코어의 actor와 연결하고 서비스 계정 매핑은 서비스 레포가 처리한다.

| 묶음 | 대표 엔터티 | 핵심 필드·관계 |
|---|---|---|
| 공간 | workspaces, actors, memberships | 공간·사용자 관계, 역할 |
| 원본 | sources, source_versions, files | 해시, 원문 위치, MIME, 전송 등급, 소유 공간 |
| 추출 | document_blocks, source_spans | 페이지·블록 ID, 본문, 좌표(제공 시), 파서 버전 |
| 개인 사실 | experiences, claims, claim_evidence | 기간, 본인 역할, 확인 상태, 근거 |
| 지식 | concepts, knowledge_edges, notes | 관계 유형, 근거, 작성 방식, 확인 상태 |
| 개인화 | goals, preferences | 목표별 설정, 출처, 수정 이력 |
| 관심 | watchlists, watch_sources, watch_rules | 회사·직무·조건·출처·주기·예산 |
| 공고 | job_candidates, jobs, job_versions | 추천 후보, 저장 상태, 원문·마감·요건·버전 |
| 지원 | applications, application_stages | 지원 목표, 전형, 일정, 실제 제출본 |
| 문서 | artifacts, artifact_versions, artifact_claims | 구조화 본문, 근거, 버전, 확정 여부 |
| 학습 | assessment_requirements, study_items, attempts, reviews | 전형별 요구, 문제·풀이, 정오·복습 |
| 실행 | runs, run_events, approvals, outbox | 상태, 비용, 재개 위치, 승인 범위 |
| 검색 | chunks, embeddings, embedding_spaces | 원본 버전, 모델·차원·청킹 버전 |

공통 조건:
- 개인 관계 테이블의 외래키에도 공간 일치 제약을 둔다. UUID만 맞으면 다른 공간의 자료를 연결할 수 있게 하지 않는다.
- 시간은 UTC로 저장하되 원본 시간대와 사용자의 표시 시간대를 보존한다. 마감 시각이 없으면 추측하지 않는다.
- 크롤링 실패·로그인 필요·접근 차단과 채용 마감을 구분한다.
- 검증 상태는 최소 `extracted / self_confirmed / evidence_supported / disputed / retired`를 구분한다. 팀 성과와 본인 기여도 분리한다.
- 개인정보 원본과 제출용·공개용 사본은 다른 객체다.

## 8. 공고 저장 흐름

### 1차 범위: URL 저장

사용자가 공고 URL을 붙여넣을 때만 그 페이지 한 건을 가져온다. 여러 URL을 한 번에 붙여넣을 수 있다. 사이트를 돌아다니는 수집, 주기 재확인, 회사 구독, 조건 검색은 1차 범위에 넣지 않는다(아래 "보류" 참고).

1. URL 정규화 → 같은 공고면 기존 항목을 연다 (같은 URL 10회 등록해도 1건).
2. worker 작업으로 가져온다: HTTP 우선, 본문이 비어 있으면(동적 페이지) 격리된 headless 브라우저로 렌더링한다. 사설망·메타데이터 주소 차단(SSRF), 시간·크기 상한, 로그인 쿠키 미사용.
3. 항목 추출: 페이지의 구조화 데이터(schema.org `JobPosting`) → 알려진 채용 시스템 어댑터 → LLM 추출. 항목마다 원문 근거 위치를 남기고, 원문에 없는 값(예: 마감 시각)은 비워 `needs_review`로 둔다. 이미지 공고는 허용된 OCR을 쓴다(전송 정책 검사).
4. 사용자가 추출 결과를 확인·수정해 확정한다. 확정한 공고만 저장 공고가 된다.
5. 스냅샷: 정리 본문 + 페이지 스크린샷을 함께 보관한다. 실제 지원하면 그 시점 스냅샷을 제출 문서와 함께 고정한다.
6. 사용자가 "다시 가져오기"를 누르면 같은 과정으로 새 버전을 만들고, 내용 해시가 같으면 버전을 늘리지 않는다. 마감·문항·요건이 바뀌면 영향받는 초안을 표시한다.
7. 가져오기 실패는 `source_unavailable`, `login_required`, `rate_limited`, `needs_manual_check`로 표시하고 마감으로 처리하지 않는다. 대안으로 본문 직접 붙여넣기, 캡처 이미지·PDF 업로드를 제공한다.

확정한 공고에서 준비 항목을 만든다(O09와 연결): 미충족·확인 필요 요건 → 학습 항목 또는 경험 확인 질문, 자소서 문항 → 문항별 작성 칸(글자 수 기준 포함), 전형 절차 → 시험 준비 항목, 일정 → 오늘 화면 D-day. 저장한 공고들 사이의 요건 빈도("저장 공고 20개 중 14개가 Docker 요구")는 사용자 저장분 기준임을 표시한다.

포털 전용 수집기는 오픈소스에 포함하지 않는다. 국내에서 채용 포털 간 대량 수집이 데이터베이스 제작자 권리 침해로 판단된 사례가 있다.

### 보류: 공고 자동화

아래 관심 조건·후보 발견·주기 재확인 흐름은 추가 검토 후 설계를 확정한다. 브라우저 확장으로 보고 있는 화면을 저장하는 방식도 이때 함께 검토한다.

#### 관심 설정 (보류)

회사를 지정하는 방식, 직무·조건으로 검색하는 방식을 URL 저장에 더해 지원하는 안이다.

설정 예시(실측·상품 한도가 아니라 편집 가능한 초기 기본값):

```yaml
watchlist:
  name: AI 서비스 개발 지원
  company_ids: [사용자가_선택한_회사]
  role_keywords: [백엔드, AI 서비스, Python]
  career_levels: [신입, 주니어]
  locations: [사용자_선택]
  sources: [등록한_공식_채용페이지, 허용된_검색원]
  check_interval_hours: 24
  max_candidates_per_run: 20
  keep_candidates_days: 7
  auto_pin: false
  on_unknown_requirement: needs_review
```

#### 처리 순서 (보류)

1. 활성 관심 조건만 읽는다.
2. 검색·RSS·공식 목록 등 가능한 경로에서 제목·링크·기본 조건을 먼저 확인한다.
3. 명확한 조건 불일치는 본문을 영구 저장하지 않는다. 미확인 조건은 탈락으로 단정하지 않는다.
4. 필요한 후보만 상세 페이지를 가져와 중복·기간·요건을 검사한다.
5. 적합 후보는 추천 보관함에 짧게 저장하고, 사용자가 저장하거나 미리 승인한 규칙을 충족한 것만 영구 목록으로 전환한다.
6. 같은 공고는 정규 URL·원본 식별자로 묶고 내용 해시가 달라진 경우만 의미 있는 버전을 추가한다.
7. 정기 실행은 변경 내역만 알린다. 변화가 없으면 문서나 알림을 다시 만들지 않는다.

ETag·Last-Modified를 제공하는 출처에는 조건부 요청을 적용한다. 지원하지 않는 출처에서는 정규화된 본문의 해시와 주요 필드를 비교한다. 동적 배너·조회 수·현재 시각 변경만으로 재분석하지 않는다. [S7]

### 보존 규칙

| 대상 | 기본 제안 |
|---|---|
| 관심 없는 검색 결과 (보류 기능) | 본문 저장 안 함, 필요 시 짧은 중복 방지 식별자만 |
| 아직 저장하지 않은 추천 후보 (보류 기능) | 7일 후 정리 |
| 가져왔지만 확정하지 않은 URL | 7일 후 정리 |
| 사용자가 저장한 공고 | 사용자가 삭제할 때까지 핵심 본문·요건 유지 |
| 저장 공고의 일반 변경 이력 | 의미 있는 변경만 압축 저장, 오래된 중간본 정리 가능 |
| 실제 지원한 공고 | 지원 당시 스냅샷을 제출 문서와 함께 고정 |
| 수집 HTML·스크린샷·중간 이미지 | 검증용 단기 보존, 필요한 증빙만 별도 고정 |
| 종료한 관심 목록 (보류 기능) | 주기 수집 중지, 기존 저장 자료는 유지 |
| 기업·업계 자료 | 관심 범위 내 요약·출처·필요한 원문만 저장 |

과거 공고를 사용자가 가져오면 저장할 수 있다. 과거 자료를 배제하는 정책과 전체 시장 수집을 하지 않는 정책은 다르다.

용량 계산 예시: 공고 500개 × 정리된 본문 30KiB × 2벌 = 약 29.3MiB. 이는 단순 계산이며 이미지·PDF·DB 오버헤드·색인·백업을 제외한다. 실제 용량은 업로드 자료와 OCR 이미지·버전 보존 정책을 측정해야 한다.

## 9. 문서 파싱과 근거 적재

`업로드 → 안전 검사 → 전송 정책 → 로컬 기본 추출/외부 파서 → 결과 정규화 → 품질 검사 → 검색·경험 후보`

- 같은 공간 안에서 파일 해시·파서·모델·옵션이 같으면 재처리를 피한다.
- 외부 파서에는 승인된 자료만 보낸다. 파서 실패 시 다른 제공자로 자동 전환하는 것도 추가 전송이므로 정책을 다시 검사한다.
- provider_job_id를 저장하고 제출 후에는 상태 조회 작업으로 분리한다. 긴 HTTP 연결이나 DB 트랜잭션을 붙잡지 않는다.
- 모델·페이지 한도는 계정 설정으로 관리한다. 무료 한도를 상수나 영구 보장으로 취급하지 않는다.
- Markdown·구조 JSON·원본 페이지 매핑을 보관한다. 없는 좌표나 인식 신뢰도를 만들어 넣지 않는다.
- 요청한 페이지 범위와 반환된 범위를 비교하고 부분 완료를 표시한다.
- 원격 ZIP·HTML·이미지도 신뢰하지 않는다. 경로 탈출·과도한 압축 해제·스크립트 실행을 막는다.
- API 키·서명 URL을 로그·모델 프롬프트·브라우저에 노출하지 않는다.

## 10. 검색과 지식 연결

초기 검색은 PostgreSQL 안에서 끝낸다. 구조화 조건과 공간 권한으로 범위를 좁힌 뒤 제목·별칭·본문 검색과 pgvector 의미 검색을 결합한다. 한국어 동의어·복합어·띄어쓰기 샘플을 별도 시험한다. pg_trgm은 유사 문자열 보조이며 한국어 의미 검색의 대체로 취급하지 않는다. [S8]

임베딩은 OpenAI API와 로컬 모델(fastembed) 둘 다 같은 게이트웨이로 붙고, 설정하지 않으면 키워드 검색만 한다. 측정과 선택 근거: `docs/architecture/search.md`.

작은 개인 자료에는 정확 벡터 검색부터 측정한다. pgvector는 정확 검색과 근사 검색을 모두 지원하므로, HNSW 색인을 무조건 켜는 대신 부하 결과와 검색 재현율을 보고 추가한다. 임베딩 모델과 차원이 다른 자료를 같은 검색 공간으로 섞지 않는다. [S3]

공고 제목·일정 같은 구조화 값은 벡터화하지 않아도 된다. 상세 경험 연결이 필요한 저장 공고만 선택적으로 임베딩한다. 읽지 않을 추천 후보마다 LLM 요약·벡터를 만들지 않는다.

관계는 `요구함 / 학습함 / 적용함 / 입증함 / 보완필요` 등 명시적인 의미와 근거를 가진다. LightRAG나 별도 그래프 엔진은 기본 의존성이 아니다. 향후 같은 평가 세트에서 이득이 확인되면 SearchProvider 뒤에 추가한다.

## 11. 문서 수정·확정·제출본

문서는 구조화된 JSON을 원장으로 두고 블록에 안정적인 ID를 붙인다. Markdown·HTML·PDF·DOCX는 출력 형태다. 처음부터 두 방향의 무손실 변환을 모든 포맷에 약속하지 않는다.

수정 요청은 `artifact_id`, `base_revision`, `operations`, `evidence_ids`, `reason`, `idempotency_key`를 포함한다. 최신 버전이 다르면 409 충돌을 반환하고 자동 덮어쓰지 않는다. 적용된 초안은 새 버전으로 저장한다.

검증 대상은 이름·회사·기간·문항·글자/바이트 제한·원본 근거·문서 간 불일치다. AI 생성 문장은 원천 경력 근거로 재등록하지 않는다. 공개·제출 전에 민감 정보와 회사 기밀을 다시 검사한다.

승인에는 행위·대상·내용 해시·문서 버전·만료 시각·승인자·멱등 키를 묶는다. AI는 승인을 요청할 수 있지만 스스로 인간 승인을 생성할 수 없다. 승인 후 내용이 바뀌면 재승인이 필요하다.

실제 제출본은 당시 공고 버전과 함께 불변으로 남긴다. 이후 경력 수정은 다음 초안에 반영하며 이미 제출한 문서를 소급 변경하지 않는다. 면접 준비도 실제 제출본을 기준으로 시작한다.

### AI slop 방지 원칙

이 제품의 가치는 글 생성이 아니다. 경력의 깊은 정리, 공고와 경험의 근거 연결, 사실 검증, 면접·시험 준비가 가치다. 공고를 넣으면 자소서를 써 주는 기능은 범용 모델로 누구나 할 수 있고, 사용자 간 구별되지 않는 문장과 면접에서 방어할 수 없는 문서를 만든다.

1. **재료는 사용자에게서 나온다.** AI는 초안을 먼저 쓰지 않는다. 경험 정리는 인터뷰형 질문으로 시작한다. 본인이 한 일, 수치 결과, 선택 이유와 대안, 어려웠던 지점, 팀 성과와 본인 기여의 구분을 묻는다. 답은 근거가 연결된 경험 카드(claim + evidence)로 저장한다.
2. **근거 없는 문장은 경고한다.** 문서 문장은 artifact_claims로 브레인의 claim에 연결한다. 연결이 없는 경험·수치·역할 서술은 검증 경고 대상이다. AI가 빈칸을 그럴듯한 내용으로 채우지 않고 사용자에게 질문한다.
3. **범용 문장을 검출한다.** `artifact_validate`는 맞춤법보다 다음을 우선한다.
   - 회사 바꿔치기 시험: 회사명·직무명을 다른 값으로 바꿔도 성립하는 문장을 범용 문장으로 표시한다.
   - 구체성: 고유명사·수치·결정 이유·본인 행동이 없는 문단을 표시한다.
   - 상투어: 사용자가 편집 가능한 상투 표현 목록.
   - 다른 회사명 잔존: 이전 지원 문서를 복사하고 남은 회사·직무명.
4. **사용자 문장을 최소 수정한다.** AI 수정은 `artifact_propose_patch`의 제안으로만 하고 이유와 원문을 함께 보인다. 사실을 바꾸는 수정(참여→주도, 수치 확대)은 거부한다. 문서별로 사용자 작성분과 AI 수정분의 비율을 표시한다.
5. **쓰기 전에 지원 여부를 판단한다.** 공고 비교에서 미충족 요건이 많으면 작성 전에 보완·학습 또는 보류를 제안한다. 대량 지원·자동 지원은 기본 기능이 아니다.
6. **면접으로 역검증한다.** 제출본에서 예상 면접 질문을 만들고, 사용자가 답하지 못하는 문장을 제거 후보로 표시한다.
7. **결과를 기록하되 단정하지 않는다.** 서류·면접 결과를 문서 버전과 연결해 기록한다. 개인 단위 표본은 작으므로 원인 판단을 자동으로 확정하지 않는다.

스킬도 이 원칙을 따른다. `career-record`는 질문하는 절차를 중심으로 하고, `prepare-application`의 첫 규칙은 "AI가 먼저 쓰지 않는다"이다. 글자 수·바이트 수는 모델이 세지 않고 `artifact_validate` 결과만 사용한다.

### 요건 가시성 검사

채용 시스템은 파일 파싱, 필수 조건 확인, 공고 대비 점수화 또는 LLM 요약·순위화를 수행할 수 있다. 회사별 시스템과 기준은 공개되지 않으므로 특정 시스템이나 모델을 겨냥해 최적화하지 않는다. 목표는 사람과 기계 모두가 실제 적합성의 근거를 찾기 쉬운 문서다.

**기계 판독성 검사**: 핵심 내용의 표·이미지 의존, 비표준 섹션 이름, 모호한 날짜 형식, 공고 용어와 다른 기술명 표기(실제 사용한 기술에 한해 공고 표기를 병기하도록 제안).

**공고·문서·브레인 3자 비교**: 공고 요건마다 "이 문서만 읽었을 때 요건 충족의 명시적 근거가 있는가"를 판정하고 브레인의 근거와 겹쳐 본다.

| 브레인 근거 | 문서에 보임 | 판정 | 제안 |
|---|---|---|---|
| 있음 | 보임 | 충족 표시됨 | 유지 |
| 있음 | 안 보임 | 누락 | 해당 경험을 문서에 드러냄 |
| 없음 | 주장함 | 과장 위험 | 근거 추가 또는 문장 삭제 |
| 없음 | 없음 | 미충족 | 학습 보완 또는 지원 재검토 |

- 판정은 모델 게이트웨이(`ModelClient`) 뒤의 교체 가능한 판정 모델이 수행한다. 요건별 예/아니오 확률이나 점수를 정해진 형태로 돌려주는 모델(예: TypeSafe Jev)이나 범용 LLM(예: Gemini, Claude)을 쓸 수 있다. 한국어 공고·이력서에서의 정확도와 비용은 합성 평가 세트로 확인한 뒤 채택한다.
- 판정 모델은 대리 심사관일 뿐이다. 판정 모델의 점수를 올리는 것 자체를 목표로 삼지 않는다.
- 판정 확률은 "근거가 문서에 보이는가"에 대한 값이다. 합격 확률로 표시하지 않는다.
- 보유하지 않은 기술의 키워드 삽입, 숨김 텍스트, 심사 모델을 향한 지시문(프롬프트 인젝션)은 생성·제안하지 않는다. 문서에 그런 내용이 있으면 검증 경고로 표시한다.

## 12. AI·MCP·스킬·브라우저

### 모델 게이트웨이와 비용

모든 LLM 호출은 `career_core.llm.gateway.ModelGateway` 한 곳을 지난다. 순서는 라우트(용도 → 엔드포인트/모델) → 자료 등급 egress → 단가 확인 → 월 예산 → 호출 → 비용 계산 → 장부(`core.model_calls`) 기록이다. 상세: `docs/architecture/models.md`.

- 제공자: Anthropic(공식 SDK) 하나와 OpenAI 호환 Chat Completions(공식 `openai` SDK) 하나로 OpenAI·Gemini·xAI(Grok)·OpenRouter·Ollama·CLIProxyAPI 같은 프록시까지 붙인다. 설정은 `models.toml`(키는 환경변수 이름만).
- 단가: 제공자 공식 가격 페이지에서 옮긴 `catalog.toml`(항목별 출처·확인일·장문 구간·예고된 가격 변경). 응답에 실제 청구액을 주는 제공자(xAI)는 그 값을 우선한다. 모르면 비용은 0이 아니라 "미상"이고, 기본 설정에서는 단가 미상 종량제 모델을 호출하지 않는다.
- 구독 프록시(CLIProxyAPI 등)는 토큰만 기록하고 실지출로 세지 않는다. 원하면 API 정가 환산액을 따로 보여준다. 소비자 구독을 API처럼 쓰는 것은 제공자 약관 위반일 수 있음을 설정 예시에 적는다.
- 모니터링: `GET /api/core/usage`(일·모델·용도·엔드포인트·상태별), `personal-api usage`, `personal-api pricing`(오래된 단가·곧 바뀌는 단가·단가 없는 라우트, xAI 공식 단가 API와 대조). 대시보드 "시스템" 화면이 같은 API를 쓴다.
- 장부에는 프롬프트·응답 본문을 남기지 않는다. 앱 role은 INSERT/SELECT만 가진다.

### 호출 경로

```text
웹 작업 → REST → UseCase
외부 AI → MCP  → 같은 UseCase
예약 작업 → worker → 같은 UseCase
```

MCP는 모든 REST endpoint를 자동 노출하지 않고 업무 단위 도구만 제공한다. FastMCP는 FastAPI 안에 마운트할 수 있지만, 공식 문서도 무분별한 API 자동 변환보다 선별된 도구 설계를 권한다. [S9]

| 도구 예시 | 핵심 입력 | 결과·안전 조건 |
|---|---|---|
| brain_search | query, goal_id, filters | 권한 있는 근거만 반환 |
| evidence_get | source_span_id | 허용된 범위·원본 위치 |
| watchlist_upsert (보류) | 관심 조건, 출처, 주기 | 공고 자동화 확정 후. 정기 실행 등록은 사용자 승인 범위 |
| job_save | URL 또는 검증 자료 | 원문·확인일·미확인 항목 |
| job_compare_profile | job_id, goal_id | 충족·불충족·확인필요, 합격률 조작 금지 |
| artifact_get | artifact_id | 현재 revision·허용된 본문 |
| artifact_propose_patch | base_revision, operations, evidence | 초안 수정안 |
| artifact_validate | artifact_id, revision | 사실·형식 검증 결과 |
| approval_request | action, target, payload_hash | 승인 요청 ID, 승인 자체 아님 |
| run_start / run_status / run_cancel | workflow, input / run_id | 비동기 작업 ID·상태 |
| study_record_attempt | study_item_id, answer, result | 학습 기록, 실무 경험으로 전환 금지 |

원격 MCP는 OAuth 등 표준 인증으로 사용자와 도구 권한을 검증한다. 모델이 전달한 workspace_id를 신뢰하지 않는다. 토큰 대상·유효기간·권한을 검증하고 외부 토큰을 무검증으로 그대로 전달하지 않는다. 로컬 stdio 연결은 별도 어댑터로 제공할 수 있다. [S10]

기본 스킬은 `career-record`, `watch-jobs`, `prepare-application`, `study-assessment` 네 묶음으로 시작한다. SKILL.md와 예제·템플릿을 제공하지만 실행 권한은 서버에서 검사한다. 스킬/호스트의 지원 기능을 선언하고 검증한 조합만 배포한다. [S11, S12]

자체 실행에는 작업 큐와 필요한 LangGraph 체크포인트를 사용한다. 단순 fetch·OCR 조회는 일반 작업으로 충분하다. LangGraph의 실행 상태는 개인 사실의 원장이 아니다. [S13]

브라우저는 HTTP·공식 API로 해결되지 않는 동적 페이지에만 사용한다. 기본은 공개 정보 수집이며 개인 로그인 쿠키와 비밀 자료를 주지 않는다. Playwright MCP의 도메인 제한은 보안 격리의 대체가 아니므로 네트워크·파일·실행 권한을 별도로 제한한다. [S14]

임의 코드 실행·무제한 shell·임의 SQL 도구를 노출하지 않는다. 코딩 연습의 실행 채점은 격리 환경을 검증하기 전까지 외부 연습 도구 연결과 코드 분석으로 제공한다. 채용시험 대리 응시는 지원하지 않는다.

## 13. 개인 대시보드

원칙: 대시보드는 "오늘 무엇을 해야 하는가"로 이어져야 한다. 숫자 카드를 나열하지 않고, 상세 정보는 클릭 시 옆 패널로 연다.

| 화면 | 구성 |
|---|---|
| 오늘 | 맨 위 `마감 임박 + 안 쓴 문항`, 그다음 `확인 대기`(추출 경험 확인, 공고 변경, 승인 요청). 학습·최근 변경은 아래. 숫자 카드 나열 방식은 쓰지 않는다 |
| 지원 현황 | 칸반(관심 → 준비 중 → 제출 → 서류 → 면접 → 결과). 카드에는 회사·직무 / D-day / 미완료 문항 / 다음 행동만. 상세는 클릭해서 옆 패널 |
| 공고 상세 | 왼쪽 요건 목록, 오른쪽 선택한 요건의 근거. 충족 여부와 요건 가시성 4분류는 별도 배지 |
| 브레인 상태 | 지식 그래프 대신 "확인·보강할 경험 목록"이 기본. 경험을 누르면 원문과 AI 추출 내용을 나란히 |
| 문서 | 중앙에 글, 오른쪽에 검사·근거 패널. 글자 수와 사용자 작성 비율은 작게, 다른 회사명 같은 위험 경고는 명확하게 |
| 학습 | 시험별 준비 목록과 `오늘 복습할 오답` 중심. 큰 성취도 차트는 후순위 |
| 회고 | 지원 결과와 당시 문서 버전을 묶은 타임라인. 표본이 적다는 안내를 결과 바로 옆에 |
| 시스템 | 별도 메뉴 하단. AI 작업·비용·외부 전송·백업·제공자 연결은 평소엔 조용히, 실패나 승인 필요 때만 오늘 화면에 노출 |

보여주지 않는 것: 합격 확률, 지원 건수 경쟁 지표, 메인 화면의 거대한 지식 그래프, 업로드 파일 목록 중심 화면.

PC는 공고/문항·편집기·근거의 다중 패널을, 모바일은 공고 저장·짧은 메모·학습·승인·문서 확인처럼 한 작업에 집중하는 단계형 화면을 쓴다. 초기 실시간 공동 편집은 제외하고 낙관적 버전 충돌 처리를 우선한다.

### 시각 스타일

- 따뜻한 회백색 배경 + 흰 작업 영역 + 청록색 포인트 + 얇은 구분선.
- 한글 글꼴 Pretendard(SIL OFL 1.1, 외부 자료 라이선스 목록에 기록). 목록 14px 전후, 문서 본문 16px 전후.
- 둥근 모서리 6~8px로 절제.
- 색은 "AI가 썼다"를 강조하는 데 쓰지 않고 `확인됨 / 확인 필요 / 근거 없음`을 구분하는 데 쓴다. 색만으로 구분하지 않고 배지 문구를 함께 둔다.
- 시각 참고: [Linear 레퍼런스](https://styles.refero.design/style/90ce5883-bb24-4466-93f7-801cd617b0d1). 웹사이트 스타일 참고용이며 칸반·에디터 UX를 검증한 템플릿은 아니다.

## 14. 기본 보안과 운영

개인용도 로그인·세션 만료·HTTPS·권한 검사가 있어야 한다. 로컬 전용 개발 모드와 인터넷 배포 모드를 분리하고 공개 주소에서는 개발 무인증 모드를 허용하지 않는다. 세션은 HttpOnly 쿠키를 기본으로 하고 CSRF·Origin·로그인 시도 제한·세션 폐기를 함께 적용한다.

모든 URL 입력은 SSRF·리다이렉트·사설망·메타데이터 주소를 검사한다. 파일 접근에는 MIME·크기·다운로드 권한·경로 정규화를 적용한다. 원문·세션·토큰은 로그에서 제외한다.

DB 앱 계정과 마이그레이션 계정은 분리한다. RLS는 추가 방어이며 앱 권한 검사도 유지한다. DB 소유자·슈퍼유저·BYPASSRLS의 우회를 고려한다. 작업 큐와 체크포인트 같은 라이브러리 테이블도 사용자 API로 직접 노출하지 않는다. [S15]

백업은 일관된 DB 백업과 원본 파일 manifest를 함께 보관하고 서버 밖 암호화 복사본을 둔다. 실행 중인 DB 데이터 폴더를 단순 복사하지 않는다. 복원 훈련으로 유효성을 확인한다. 백업에서 복원한 삭제 자료가 다시 노출되지 않도록 삭제 기록의 재적용 절차도 둔다.

## 15. 배포·버전·서비스 연동 계약

코어 패키지에는 공개 인터페이스·스키마·마이그레이션이 포함된다. 설치 앱은 `create_app()` 또는 명시적인 router 등록으로 코어를 조립한다. 기본 인증·전송·예산 정책은 외부에서 주입하되 빈 설정으로 모든 권한이 열리지 않게 한다.

개인 배포는 코어 migration과 personal identity migration을 적용한다. 서비스 배포는 같은 코어 migration과 서비스 migration을 적용한다. 각 테이블의 변경 권한은 소유 레포에만 있다. 하나의 배포 명령이 잠금을 얻고 정해진 순서로 수행하며, API 시작마다 자동으로 schema를 변경하지 않는다. Alembic의 브랜치·의존성을 활용할 수 있지만 복수의 임의 migration 실행기는 금지한다. [S16]

Python wheel·UI·TS client는 호환 조합을 manifest로 배포한다. 개발 중 editable install은 가능하나 배포는 고정 버전·해시를 사용한다. 서비스의 main branch 추적이나 운영 중 즉시 최신 업데이트는 하지 않는다.

내보내기는 manifest·원본·확정 경험·문서 버전·관심 설정·학습 기록을 포함한다. 키·세션·쿠키·서비스 결제정보는 제외한다. 가져오기는 dry-run, schema 호환 검사, 해시 검사, ID 재매핑, 중복 정책을 갖춘다. 개인↔서비스 양방향 상시 동기화는 이번 범위가 아니다.

## 17. 고정 회귀 시험

1. 다른 workspace의 파일 ID·claim ID·run ID로 조회/수정/내보내기를 요청해도 실패한다.
2. MCP에서 직접 요청해도 웹앱과 같은 정책이 적용된다.
3. 같은 URL을 10회 등록해도 공고가 중복 생성되지 않는다.
4. 동일 본문을 10회 다시 가져와도 버전·임베딩 수가 불필요하게 늘지 않는다.
5. 마감·문항·요건이 바뀌면 변경 필드와 영향받은 초안을 표시한다.
6. 사이트 접근 실패는 채용 마감으로 처리하지 않는다.
7. 금지 등급 자료의 OCR·LLM 전송을 거절한다.
8. 파싱 중 worker가 종료되어도 provider job을 조회하고 중복 제출을 최소화한다.
9. base_revision이 오래된 수정은 덮어쓰지 않는다.
10. 승인 후 문서·대상이 변경되면 기존 승인을 사용할 수 없다.
11. AI 생성 초안이 경력의 원천 증빙으로 확정되지 않는다.
12. 제출본은 이후 경력 수정에도 바뀌지 않는다.
13. 복원된 공간의 원본·관계·문서가 연결되어 있다.
14. 외부 API 한도 초과 시 자동 유료 전환 없이 대기·실패 사유를 표시한다.
15. 외부 자료에 있는 명령으로 다른 자료 전송·shell 실행이 발생하지 않는다.
16. 회사명만 바꿔도 성립하는 문장과 다른 회사명이 남은 문장이 검증 경고로 표시된다.
17. 브레인 근거가 없는 경험·수치 서술은 경고되고, AI 수정안이 사실(역할·수치)을 바꾸면 거부된다.
18. 요건 가시성 검사가 누락(근거 있음·문서에 없음)과 과장 위험(근거 없음·문서 주장)을 구분한다.
19. 키워드 삽입·숨김 텍스트·심사 모델 대상 지시문을 생성하지 않고, 문서에 있으면 경고한다.
20. 글자·바이트 수는 모델 출력이 아니라 문항 설정(공백·줄바꿈·인코딩 기준)에 따른 코드 계산 결과다.
21. 단가를 모르는 종량제 모델 호출과 월 예산을 넘긴 호출은 제공자에 보내기 전에 거부되고, 거부도 장부에 남는다.
22. 구독 프록시 호출은 실지출 합계와 예산에 들어가지 않는다.
23. AI 추출 주장 중 원문에서 인용을 찾지 못한 것은 저장되지 않고, 저장된 인용은 원문 블록의 해당 범위와 글자 단위로 같다.
24. 확인 권한(approve) 없는 사람이나 팀/본인 구분이 없는 주장은 확정 상태가 될 수 없다 (앱 규칙 + DB CHECK).
25. API 임베딩은 restricted 자료를 색인하지 않고, 모델·차원이 다른 벡터를 한 검색에 섞지 않으며, 고친 본문의 옛 벡터를 쓰지 않는다.
