# 검색 (O05)

브레인 검색은 PostgreSQL 안에서 끝난다. 키워드 검색은 항상 켜져 있고, 의미 검색(임베딩)은 설정했을 때만 더한다.

## 구조

```text
질문 ─┬─ 키워드: pg_trgm word_similarity + 낱말 부분 일치(ILIKE) ── 원본 테이블을 그대로 (항상 최신)
      └─ 의미: 질문 임베딩 → pgvector 코사인 거리(정확 검색) ── 본문 해시가 같은 벡터만
            ↓
       RRF(k=60)로 합침. 점수가 같으면 원문 낱말이 실제로 들어 있는 결과가 앞.
```

- 대상: 폐기되지 않은 주장(`claim`), 원본별 최신 파싱 블록(`block`), 인터뷰 답(`answer`).
- 학습 기록(c0013): 학습 메모(`study_note`, 메모가 있는 학습 기록)와 오답(`study_mistake`, 문제·내 답·정답·이유).
  - **기본 검색에는 들어가지 않는다.** `kinds=study_note,study_mistake`로 고를 때만. 문서 근거 검색은 그대로 주장·블록·답만 본다. MCP `search_brain`은 `include_study: true`를 줄 때만 학습 기록을 더하고 학습 결과마다 `note: "study, not experience"`를 붙인다 (c0021, `mcp.md`).
  - 결과마다 `record`가 붙는다: `experience`(주장·블록·답) 또는 `study`(학습 기록). 학습 결과는 `study_item_id`·`study_title`도. 웹 검색은 모든 종류를 묻고 학습 결과에 "학습 기록 · 경험 아님"을 붙인다.
  - 같은 공간·등급 규칙: 학습 메모는 `private` 등급으로 다룬다 (외부 임베딩은 엔드포인트가 `private`을 허용할 때만).
- 공간 격리: RLS. 검색 SQL은 세션의 공간만 본다. 시험: 같은 자료를 두 공간에 넣고 30문항 모두에서 다른 공간 결과 0건.
- 한국어: 조사가 붙은 원문(`시간을`)에도 낱말(`시간`) 부분 일치로 걸린다. DB 로캘이 한글을 글자로 분류해야 trigram이 동작한다 (`en_US.utf8`·`C.UTF-8` 확인, `C`는 불가).
- HNSW 등 근사 색인은 두지 않았다. 개인 자료 규모에서는 정확 검색이 충분하고, 재현율 손실이 없다.

## 임베딩: API 또는 로컬

`models.toml`의 `routes.embed` 하나로 고른다. 없으면 키워드 검색만 (가장 가볍다).

| 방식 | 설정 | 비용·자원 | 자료 등급 |
|---|---|---|---|
| OpenAI API | `embed = "openai/text-embedding-3-small"` (+ `[embedding] dimensions`) | $0.02 / 1M 토큰, 로컬 메모리 거의 없음 | 엔드포인트 `data_classes`가 허용한 등급만 (restricted는 항상 제외) |
| 로컬 (fastembed, ONNX/numpy, torch 없음) | `preset = "local"` 엔드포인트 + `embed = "<그 이름>/<모델>"` | 무료, 모델 파일 + 사용 중 RAM (아래) | 모든 등급 (기계 밖으로 안 나감) |

- 임베딩도 대화 호출과 같은 게이트웨이를 지난다: egress → 단가 → 월 예산 → 호출 → 장부(`purpose = 'embed'`).
- 검색어 임베딩도 외부 전송이다. API 임베딩이면 `egress` 권한이 있는 사람만 의미 검색을 쓰고, 나머지는 키워드 결과에 `semantic_note = egress_scope_required`.
- 벡터는 `(대상, 공간)`마다 하나. 공간 = `제공자:모델:차원설정`. 다른 공간끼리는 섞지 않는다. 설정을 바꾸면 `personal-api reindex`.
- 색인은 worker 작업(`kind = 'embed'`, 공간당 대기 1개)이다. 파싱 완료·추출·주장 추가/수정·인터뷰 답·학습 메모·오답에서 예약된다. 본문 해시가 같으면 다시 만들지 않는다.
- 실행 중 바뀐 항목 (c0013): 예약은 공간별 advisory lock을 **공유**로, 색인 작업의 "남은 대상 확인 → 작업 끝냄"은 같은 lock을 **배타**로 잡는다. 남은 대상이 없을 때만 같은 트랜잭션에서 작업을 `done`으로 바꾸므로, 실행 중에 들어온 예약은 (1) 아직 commit 전이면 확인이 끝날 때까지 기다렸다가 끝난 작업 뒤에 새 작업을 넣고, (2) 이미 commit했으면 확인에서 바뀐 대상이 보여 한 바퀴 더 돈다. 대상이 남으면 핸들러는 `retry_after=0`으로 곧바로 다시 돈다. 시험: 임베딩 도중 주장을 고쳐도 마지막 벡터가 새 본문 해시.
- 로컬 모델은 처음 쓸 때 올리고 `CAREER_EMBED_IDLE_SECONDS`(기본 300초) 동안 안 쓰면 내린다.

- 결론: 기본값은 키워드만. 가벼운 서버에서 의미 검색이 필요하면 OpenAI `text-embedding-3-small`, 오프라인이면 `potion-multilingual-128M`(`mmap=True` + 어휘 자르기로 모델 단독 ~0.44GB).
- OpenAI 임베딩 (2026-11-17 측정, 결합 검색 기준): `text-embedding-3-small`은 1536차원과 `dimensions = 512` 모두 키워드만보다 다른 표현 R@5가 4/6 → 5/6으로 오르고 R@1은 25/30 그대로다 (512차원으로 줄여도 같은 결과라 저장·검색이 가벼운 512를 권한다). `text-embedding-3-large`는 R@1 28/30, 다른 표현 R@1 2/6 → 4/6으로 이 표에서 가장 좋지만 단가가 6.5배($0.13 / 1M)다. 평가 1회는 합성 글 약 3,500자 + 질문 30개라 수천 토큰, 모델과 상관없이 $0.001 미만이다.
- 표본이 작다. 실제 자료로 늘린 평가 세트는 사용자 공간 밖(임시 DB)에서만 돌린다.

## potion 어휘 자르기 (2026-11-17)

potion-multilingual-128M의 Unigram 토크나이저(어휘 500,353개)가 상주 메모리의 대부분이었다. 남길 글자(ASCII·라틴 확장·한글·한자·일반/CJK 문장부호·화살표·기호·원문자·전각)만으로 된 토큰 297,125개만 남기고 임베딩 행도 같이 잘라, 처음 쓸 때 캐시(`<model_dir>/career-trimmed/<모델>-<revision>-v1/`)에 한 번 만든다. 만드는 일은 별도 프로세스에서 약 1초, 최대 RSS ~0.44GB이고 같은 원본이면 같은 파일이 나온다. Unigram 분할은 토큰 점수로만 정해지므로 남긴 글자만으로 된 글은 분할이 그대로이고 벡터가 비트 단위로 같다(합성 평가 글 전부 차이 0). 남기지 않은 글자(키릴·아랍·가나 문자, 이모지 등)는 모르는 토큰이 되어 평균에서 빠진다(이모지가 섞인 문장은 코사인 0.83). 모델 단독 최대 RSS ~0.95GB → ~0.44GB, 모델 파일 0.51GB → 0.30GB(+토크나이저 18MB → 11MB). 합성 30문항: R@1 27/30, R@5 29/30, 다른 표현 R@5 5/6으로 그대로다. `CAREER_EMBED_TRIM=0`이면 원래 모델을 쓴다. 이미 만든 색인은 다시 만들 필요가 없다(한국어·영어 글의 벡터가 같다). 남기지 않은 글자가 든 글까지 맞추려면 `personal-api reindex`.

## RLS 아래 trigram 색인 (2026-11-17 측정, 채택하지 않음)

키워드 질의는 RLS 때문에 trigram GIN 색인을 못 쓴다 (pg_trgm 연산자가 LEAKPROOF가 아니라 정책 조건보다 먼저
색인 조건으로 쓸 수 없다). 대안으로 소유자 권한 SECURITY DEFINER 함수(`core.search_keyword_ids`: 모든 표에
`workspace_id = core.current_workspace_id()`를 직접 걸고 `<%`·ILIKE로 후보와 점수를 고른 뒤, 바깥 쿼리가 RLS
아래에서 기본 키로 다시 읽음, `search_path` 고정, 앱 role만 EXECUTE)를 시험했다.

- 자료: 공간 2개 × 주장 20,000·블록 3,000(절반은 옛 파싱)·인터뷰 답 1,000 (합성), PostgreSQL 17, Apple Silicon, 임시 DB.
- 결과는 이전과 같았다 (질문 12개 × 종류 5가지 × k 2가지 = 120경우 모두 같은 순서·점수).
- 격리: 공간 문맥 없음/빈 값/없는 공간 → 0행, 전체 일치 패턴으로 불러도 다른 공간 ID 0개, NULL·따옴표 인자 0행.
- 속도 (질의별 중앙값, 이전 → 함수):
  - 3글자 이상 드문 낱말만 있는 질의: 135 → 4ms, 132 → 4ms, 136 → 15ms (없는 낱말), `Kubernetes` 142 → 74ms.
  - **2글자 한국어 낱말이 든 질의**(`배포`, `결제 시스템`, `응답 시간 개선`, `Kafka 지투`): 145 → 261ms, 223 → 331ms,
    203 → 347ms, 160 → 299ms. 2글자 낱말은 `%배포%`에서 trigram이 나오지 않아 색인이 거르지 못하고,
    planner가 순차 훑기를 고르면 `<%` 계산이 더해져 더 느리다.
  - 전체 p50 155 → 141ms, p95 222 → 346ms.
  - 소유자가 superuser가 아니면(관리형 DB 등) `FORCE RLS`가 함수 안에서도 적용돼 색인을 못 쓴다: 142.7 → 141.4ms (같음).
- 결론: 한국어 질의 대부분(2글자 낱말)에서 느려지고, 소유자가 superuser일 때만 효과가 있어 "뚜렷이 빠름"이 아니다.
  RLS를 건너뛰는 함수를 하나 더 두는 위험에 견줄 이득이 없어 넣지 않았다. 지금 방식(RLS + 순차 훑기)은
  주장 2만 개에서 p50 ~150ms다.
