# 검색 (O05)

브레인 검색은 PostgreSQL 안에서 끝난다. 키워드 검색은 항상 켜져 있고, 의미 검색(임베딩)은 설정했을 때만 더한다.

## 구조

```text
질문 ─┬─ 키워드: pg_trgm word_similarity + 낱말 부분 일치(ILIKE) ── 원본 테이블을 그대로 (항상 최신)
      └─ 의미: 질문 임베딩 → pgvector 코사인 거리(정확 검색) ── 본문 해시가 같은 벡터만
            ↓
       RRF(k=60)로 합침. 점수가 같으면 원문 낱말이 실제로 들어 있는 결과가 앞.
```

- 대상: 폐기되지 않은 주장(`claim`), 원본별 최신 파싱 블록(`block`), 인터뷰 답(`answer`).
- 학습 기록(c0013): 학습 메모(`study_note`, 메모가 있는 학습 기록)와 오답(`study_mistake`, 문제·내 답·정답·이유).
  - **기본 검색에는 들어가지 않는다.** `kinds=study_note,study_mistake`로 고를 때만. 문서 근거 검색은 그대로 주장·블록·답만 본다. MCP `search_brain`은 `include_study: true`를 줄 때만 학습 기록을 더하고 학습 결과마다 `note: "study, not experience"`를 붙인다 (c0021, `mcp.md`).
  - 결과마다 `record`가 붙는다: `experience`(주장·블록·답) 또는 `study`(학습 기록). 학습 결과는 `study_item_id`·`study_title`도. 웹 검색은 모든 종류를 묻고 학습 결과에 "학습 기록 · 경험 아님"을 붙인다.
  - 같은 공간·등급 규칙: 학습 메모는 `private` 등급으로 다룬다 (외부 임베딩은 엔드포인트가 `private`을 허용할 때만).
- 공간 격리: RLS. 검색 SQL은 세션의 공간만 본다. 시험: 같은 자료를 두 공간에 넣고 30문항 모두에서 다른 공간 결과 0건.
- 한국어: 조사가 붙은 원문(`시간을`)에도 낱말(`시간`) 부분 일치로 걸린다. 기술명 별칭으로 검색어를 넓히고(아래), 선택 extra `korean`을 깔면 형태소 분석으로 검색어 낱말을 고른다(아래). DB 로캘이 한글을 글자로 분류해야 trigram이 동작한다 (`en_US.utf8`·`C.UTF-8` 확인, `C`는 불가).
- HNSW 등 근사 색인은 두지 않았다. 개인 자료 규모에서는 정확 검색이 충분하고, 재현율 손실이 없다.

## 임베딩: API 또는 로컬

`models.toml`의 `routes.embed` 하나로 고른다. 예시 설정(`models.example.toml`)의 기본은 `openai/text-embedding-3-large` + `[embedding] dimensions = 1024`다. 라우트가 없거나 그 엔드포인트의 키 환경변수가 비어 있으면 색인·검색어 임베딩을 부르지 않고(장부 기록도 없음) 키워드 검색만 한다. 검색 결과의 `semantic_note`는 각각 `no_embedding_route`, `embedding_api_key_missing`.

| 방식 | 설정 | 비용·자원 | 자료 등급 |
|---|---|---|---|
| OpenAI API | `embed = "openai/text-embedding-3-large"` + `[embedding] dimensions = 1024` (기본) 또는 `text-embedding-3-small` | $0.13 / $0.02 per 1M 토큰, 로컬 메모리 거의 없음 | 엔드포인트 `data_classes`가 허용한 등급만 (restricted는 항상 제외) |
| 로컬 (fastembed, ONNX/numpy, torch 없음) | `preset = "local"` 엔드포인트 + `embed = "<그 이름>/<모델>"` | 무료, 모델 파일 + 사용 중 RAM (아래) | 모든 등급 (기계 밖으로 안 나감) |

- 임베딩도 대화 호출과 같은 게이트웨이를 지난다: egress → 단가 → 월 예산 → 호출 → 장부(`purpose = 'embed'`).
- 검색어 임베딩도 외부 전송이다. API 임베딩이면 `egress` 권한이 있는 사람만 의미 검색을 쓰고, 나머지는 키워드 결과에 `semantic_note = egress_scope_required`.
- 벡터는 `(대상, 공간)`마다 하나. 공간 = `제공자:모델:차원설정`. 다른 공간끼리는 섞지 않는다. 설정을 바꾸면 `personal-api reindex`.
- 색인은 worker 작업(`kind = 'embed'`, 공간당 대기 1개)이다. 파싱 완료·추출·주장 추가/수정·인터뷰 답·학습 메모·오답에서 예약된다. 본문 해시가 같으면 다시 만들지 않는다.
- 실행 중 바뀐 항목 (c0013): 예약은 공간별 advisory lock을 **공유**로, 색인 작업의 "남은 대상 확인 → 작업 끝냄"은 같은 lock을 **배타**로 잡는다. 남은 대상이 없을 때만 같은 트랜잭션에서 작업을 `done`으로 바꾸므로, 실행 중에 들어온 예약은 (1) 아직 commit 전이면 확인이 끝날 때까지 기다렸다가 끝난 작업 뒤에 새 작업을 넣고, (2) 이미 commit했으면 확인에서 바뀐 대상이 보여 한 바퀴 더 돈다. 대상이 남으면 핸들러는 `retry_after=0`으로 곧바로 다시 돈다. 시험: 임베딩 도중 주장을 고쳐도 마지막 벡터가 새 본문 해시.
- 로컬 모델은 처음 쓸 때 올리고 `CAREER_EMBED_IDLE_SECONDS`(기본 300초) 동안 안 쓰면 내린다.

- 표본이 작다. 실제 자료로 늘린 평가 세트는 사용자 공간 밖(임시 DB)에서만 돌린다.

## 임베딩만 비교 (2026-11-17, `python -m career_core.evals.embed_eval`)

위 30문항은 원문 낱말이 든 질문이 많아 키워드 검색이 거의 다 찾으므로 임베딩 차이가 안 보인다(모두 R@5 29/30). 그래서 키워드 검색을 빼고 벡터 순위만 잰다. 합성 글 40개(한국어 32, 영어 8; 같은 기술을 다른 일에 쓴 글을 섞음)와 정답 글의 낱말을 되도록 겹치지 않게 쓴 질문 52개: 한국어 바꿔 말하기 24(`온콜 운영 체계` → "장애 알림 당번 순번표"), 영어 질문 → 한국어 글 12, 한국어 질문 → 영어 글 7, 약어·한글 표기 9(`k8s`, `카프카`, `LCP`). 글 40개 중 1위·5위 안에 정답이 오는지와 MRR.

| 모델 (차원) | R@1 | R@5 | MRR | 한국어 바꿔 말하기 R@5 | 영→한 R@5 | 한→영 R@5 | 약어 R@5 | 단가 / 1M 토큰 |
|---|---|---|---|---|---|---|---|---|
| OpenAI 3-small (512) | 25/52 | 36/52 | 0.607 | 15/24 | 10/12 | 3/7 | 8/9 | $0.02 |
| OpenAI 3-small (1024) | 26/52 | 37/52 | 0.611 | 15/24 | 10/12 | 4/7 | 8/9 | $0.02 |
| OpenAI 3-small (1536, 원래 차원) | 25/52 | 36/52 | 0.600 | 14/24 | 10/12 | 4/7 | 8/9 | $0.02 |
| OpenAI 3-large (1024, **기본**) | **40/52** | 47/52 | **0.837** | 20/24 | 12/12 | 6/7 | 9/9 | $0.13 |
| OpenAI 3-large (3072, 원래 차원) | 39/52 | **48/52** | 0.828 | 21/24 | 12/12 | 6/7 | 9/9 | $0.13 |
| 로컬 potion-multilingual-128M (256) | 22/52 | 34/52 | 0.545 | 17/24 | 7/12 | 3/7 | 7/9 | 무료, RAM ~0.44GB |
| 로컬 multilingual-e5-large (1024) | 32/52 | 47/52 | 0.746 | 20/24 | 12/12 | 6/7 | 9/9 | 무료, RAM ~3.7GB |

- **차원은 정확도를 거의 바꾸지 않는다.** 3-small은 512·1024·1536이 오차 범위 안(R@5 36~37/52)이고, 3-large도 1024와 3072가 같다. 차원을 줄이면 저장(벡터 1개 512차원 = 2KB, 3072차원 = 12KB)과 검색 계산이 가벼워진다. pgvector HNSW 색인은 2,000차원까지라 3-large를 그대로 쓰면 나중에 색인을 붙일 수 없다는 점도 1024를 고르는 이유다.
- **차이를 만드는 것은 모델이다.** 3-large는 3-small보다 R@5가 11문항 많다. 특히 한국어 바꿔 말하기(15 → 20/24)와 영어 질문으로 한국어 글 찾기(10 → 12/12).
- **다국어:** 셋 다 한국어·영어를 한 공간에 둔다(영→한 질문도 찾는다). 다만 한국어 질문으로 영어 글을 찾는 것은 모든 모델이 약하다(7문항 중 3~6).
- **비용:** 이 평가 1회는 2,352 토큰(3-small $0.00005, 3-large $0.0003). 개인 자료 전체(수십만 토큰)를 색인해도 3-large가 몇 센트라 정확도가 나은 3-large 1024차원을 기본으로 둔다. 비용을 더 줄이려면 `embed = "openai/text-embedding-3-small"` + `dimensions = 512`로 바꾸고 `personal-api reindex`.
- 실제 검색은 키워드 + 의미 결합(RRF)이라 이 표보다 결과가 좋다(원문 낱말이 있으면 키워드가 찾는다). 이 표는 낱말이 겹치지 않는 질문에서의 차이다.
- 표본이 작다(52문항). ±2문항 차이는 의미를 두지 않는다.

## potion 어휘 자르기 (2026-11-17)

potion-multilingual-128M의 Unigram 토크나이저(어휘 500,353개)가 상주 메모리의 대부분이었다. 남길 글자(ASCII·라틴 확장·한글·한자·일반/CJK 문장부호·화살표·기호·원문자·전각)만으로 된 토큰 297,125개만 남기고 임베딩 행도 같이 잘라, 처음 쓸 때 캐시(`<model_dir>/career-trimmed/<모델>-<revision>-v1/`)에 한 번 만든다. 만드는 일은 별도 프로세스에서 약 1초, 최대 RSS ~0.44GB이고 같은 원본이면 같은 파일이 나온다. Unigram 분할은 토큰 점수로만 정해지므로 남긴 글자만으로 된 글은 분할이 그대로이고 벡터가 비트 단위로 같다(합성 평가 글 전부 차이 0). 남기지 않은 글자(키릴·아랍·가나 문자, 이모지 등)는 모르는 토큰이 되어 평균에서 빠진다(이모지가 섞인 문장은 코사인 0.83). 모델 단독 최대 RSS ~0.95GB → ~0.44GB, 모델 파일 0.51GB → 0.30GB(+토크나이저 18MB → 11MB). 합성 30문항: R@1 27/30, R@5 29/30, 다른 표현 R@5 5/6으로 그대로다. `CAREER_EMBED_TRIM=0`이면 원래 모델을 쓴다. 이미 만든 색인은 다시 만들 필요가 없다(한국어·영어 글의 벡터가 같다). 남기지 않은 글자가 든 글까지 맞추려면 `personal-api reindex`.

|---|---|---|---|---|---|---|---|

## RLS 아래 trigram 색인 (2026-11-17 측정, 채택하지 않음)

키워드 질의는 RLS 때문에 trigram GIN 색인을 못 쓴다 (pg_trgm 연산자가 LEAKPROOF가 아니라 정책 조건보다 먼저
색인 조건으로 쓸 수 없다). 대안으로 소유자 권한 SECURITY DEFINER 함수(`core.search_keyword_ids`: 모든 표에
`workspace_id = core.current_workspace_id()`를 직접 걸고 `<%`·ILIKE로 후보와 점수를 고른 뒤, 바깥 쿼리가 RLS
아래에서 기본 키로 다시 읽음, `search_path` 고정, 앱 role만 EXECUTE)를 시험했다.

- 자료: 공간 2개 × 주장 20,000·블록 3,000(절반은 옛 파싱)·인터뷰 답 1,000 (합성), PostgreSQL 17, Apple Silicon, 임시 DB.
- 결과는 이전과 같았다 (질문 12개 × 종류 5가지 × k 2가지 = 120경우 모두 같은 순서·점수).
- 격리: 공간 문맥 없음/빈 값/없는 공간 → 0행, 전체 일치 패턴으로 불러도 다른 공간 ID 0개, NULL·따옴표 인자 0행.
- 속도 (질의별 중앙값, 이전 → 함수):
  - 3글자 이상 드문 낱말만 있는 질의: 135 → 4ms, 132 → 4ms, 136 → 15ms (없는 낱말), `Kubernetes` 142 → 74ms.
  - **2글자 한국어 낱말이 든 질의**(`배포`, `결제 시스템`, `응답 시간 개선`, `Kafka 지투`): 145 → 261ms, 223 → 331ms,
    203 → 347ms, 160 → 299ms. 2글자 낱말은 `%배포%`에서 trigram이 나오지 않아 색인이 거르지 못하고,
    planner가 순차 훑기를 고르면 `<%` 계산이 더해져 더 느리다.
  - 전체 p50 155 → 141ms, p95 222 → 346ms.
  - 소유자가 superuser가 아니면(관리형 DB 등) `FORCE RLS`가 함수 안에서도 적용돼 색인을 못 쓴다: 142.7 → 141.4ms (같음).
- 결론: 한국어 질의 대부분(2글자 낱말)에서 느려지고, 소유자가 superuser일 때만 효과가 있어 "뚜렷이 빠름"이 아니다.
  RLS를 건너뛰는 함수를 하나 더 두는 위험에 견줄 이득이 없어 넣지 않았다. 지금 방식(RLS + 순차 훑기)은
  주장 2만 개에서 p50 ~150ms다.

## 기술명 별칭으로 넓히기 (2026-11-17)

### 복합명사 낱말 일치: 한 낱말로 센다 (2026-11-17, c19)

형태소 모드에서 요건 `머신러닝 모델 서빙 경험`이 낱말 넷(머신·러닝·모델·서빙, "두 개 이상" 기준)이 되어, 주장
`머신러닝 스터디에서 논문을 매주 읽었다`가 `머신`·`러닝` 두 낱말로 기준을 넘었다 (규칙 기반은 `머신러닝` 하나라 넘지 않는다).

- 정한 것: 요건의 **한 어절(띄어 쓰지 않은 한글 묶음)에서 나온 내용어는 한 낱말로 센다** (`Terms.groups`). 묶음은 **모든 부분이
  있을 때만** 맞은 것으로 본다. 앞부분만 같은 경우(`결제시스템` ↔ `결제 화면`, `캐시서버 도입` ↔ `새 서버를 도입`)는 맞지 않는다.
  띄어 써도 부분이 모두 있으면 맞는다(`결제시스템` ↔ `결제 시스템을`).
- 이유: 한국어 복합명사는 마지막 명사가 중심이고 앞 명사는 꾸밈이다. 앞부분만 같으면 다른 것을 가리키고(결제 화면 ≠ 결제 시스템),
  뒷부분만 같으면 너무 넓다(시스템). 규칙 기반에서도 `결제시스템`은 통째로만 맞으므로 두 모드의 뜻이 같아진다.
  낱말을 나누는 것은 띄어쓰기 차이를 맞추기 위해서였지, 나눈 조각 수로 기준을 채우기 위해서가 아니다.
- 묶음은 요건 전체를 분석한 결과를 원문 위치(`content_spans`)로 어절에 나눈다. 어절만 따로 분석하면 kiwi 분할이 달라진다
  (`커버리지`가 문장 안과 밖에서 다르게 나뉨).
- 결과: 판정 기준선 kiwi 30/64 → 31/64 (c19만 바뀜, 규칙과 같은 33/64·21/36 — 별칭 넓히기 포함), 요건/문서 쌍 38/40 → 39/40,
  문장 쌍 18/27 → 20/27 (`자동완성` ↔ `자동 저장`, `검색엔진` ↔ `엔진 오일 … 검색 화면`). 나빠진 쌍 없음. 규칙 기반은 바뀌지 않는다 (묶음 없음).
- 버린 대안: 묶음의 아무 부분이나 맞으면 인정 — `결제시스템 개발 경험`(묶음 하나)이 `결제 화면`에 맞아 더 느슨해진다.
  마지막 부분(중심 명사)만 보면 `인사 시스템`이 `결제시스템`에 맞는다.

### 쉬면 내리기 (`CAREER_KOREAN_IDLE_SECONDS`, 2026-11-17)

로컬 임베딩(`CAREER_EMBED_IDLE_SECONDS`)처럼 kiwi 모델을 **처음 쓸 때 올리고 `CAREER_KOREAN_IDLE_SECONDS`(기본 300초) 동안 안 쓰면
내린다.** `0`이면 계속 들고 있다. 결과 기억(512개)도 같이 비우고, 다음 분석에서 다시 올린다(~0.4초, 결과 같음).

- 타이머는 분석기마다 하나다: 마지막 사용 시각만 적고, 타이머가 울리면 남은 시간만큼 다시 건다 (요건마다 부르는 검사에서 부를 때마다 스레드를 만들지 않는다).
- 시험은 가짜 분석기(`KiwiAnalyzer(factory=…, clock=…)`)로 올림·내림·다시 올림과 실제 타이머를 본다 (kiwipiepy 없이 돈다).
- **측정 (macOS arm64, `footprint`)**: 올린 뒤 394MB → 처음 내린 뒤 234MB. 다시 올리면 ~367MB, 그 뒤로는 내려도 ~338MB에 머문다.
  Kiwi 객체는 실제로 풀리지만(참조 없음) 프로세스 할당자가 풀린 메모리를 운영체제에 다 돌려주지 않는다(`malloc_zone_pressure_relief`도 효과 없음).
  즉 프로세스 안에서 내리기는 처음 한 번 ~0.16GB만 돌려주고 그 뒤로는 거의 돌려주지 않는다. Linux(glibc)는 재지 않았다.
- 확실히 돌려주려면 분석을 별도 프로세스로 옮겨야 한다 (API·worker가 같이 쓰는 분석 프로세스 하나, 쉬면 그 프로세스를 끝냄). 이번 범위 밖, 후속.

## 2글자 한국어 낱말 bigram (2026-11-17 검토, 보류)

"RLS 아래 trigram 색인"에서 남은 2글자 낱말(`배포`, `결제`)용 색인을 하나만 골라 봤다.

- pg_bigm: 쓰는 이미지(`pgvector/pgvector:pg17`)에 없다 (`/usr/share/postgresql/17/extension`에 pg_trgm만). 따로 빌드한 이미지를 요구하게 된다.
  들어 있어도 연산자(`LIKE`, `texticlike`)가 LEAKPROOF가 아니라(`pg_proc.proleakproof = f`) FORCE RLS 아래에서는 trigram과 같은 이유로 색인을 못 쓴다.
- 앱이 관리하는 bigram 표(내용 → 2글자 조각, `workspace_id` 포함): 쓰기마다 조각을 다시 만들어야 하고(주장·블록·답·학습 기록), 원본과 어긋날 수 있는 두 번째 사본이 생긴다.
  지금 순차 훑기가 주장 2만 개에서 p50 ~150ms라 개인 규모에서 얻을 것이 없다.
- 그대로 둔다. 서비스(많은 공간)에서 공간당 수만 건을 넘으면 공간별 파티션·검색 전용 요약 표와 함께 다시 잰다.
